== Executive Summary

This document provides a comprehensive plan for implementing a pluggable layout manager system in fpGUI, inspired by Java Swing's LayoutManager architecture. The goal is to enable powerful layout managers like MigLayout while maintaining backward compatibility with fpGUI's existing Align/Anchors system.

**Key Design Principles:**

* **Pluggable Architecture**: Layout managers are separate, replaceable objects
* **Backward Compatibility**: Existing Align/Anchors system continues to work
* **Flexible Constraints**: Per-widget layout hints stored as constraint objects
* **Zero-Cost Abstraction**: No performance penalty when not using layout managers

== Background: Current fpGUI Layout System

=== Overview

fpGUI currently implements layout through two complementary mechanisms:

1. **TAlign Enum**: Widgets can align to parent edges (alTop, alBottom, alLeft, alRight, alClient)
2. **TAnchors Set**: Widgets maintain fixed distances to parent edges during resize

=== TAlign System

Defined in `src/corelib/fpg_main.pas`:

[source,pascal]
----
TAlign = (alNone, alTop, alBottom, alLeft, alRight, alClient);
----

Widgets with `Align` set are positioned by the parent's `HandleAlignments` method (`src/corelib/fpg_widget.pas:1669`):

[source,pascal]
----
procedure TfpgWidget.HandleAlignments(const dwidth, dheight: TfpgCoord);
var
  alist: TList;
  n: integer;
  w: TfpgWidget;
begin
  FAlignRect := GetClientRect;
  alist := TList.Create;
  try
    // Collect all widgets with Align property
    for n := 0 to ComponentCount - 1 do
    begin
      w := TfpgWidget(Components[n]);
      if (w.Align <> alNone) and (w.Visible) then
        alist.Add(w);
    end;
    DoAlignment(alist);  // Process alignment
  finally
    alist.Free;
  end;

  // Handle anchors for alNone widgets...
end;
----

The `DoAlignment` method processes widgets in order:

[source,pascal]
----
procedure TfpgWidget.DoAlignment(AAlign: TAlign);
begin
  for n := 0 to alist.Count - 1 do
  begin
    w := TfpgWidget(alist[n]);
    case w.Align of
      alTop:    // Dock to top, shrink FAlignRect
      alBottom: // Dock to bottom, shrink FAlignRect
      alLeft:   // Dock to left, shrink FAlignRect
      alRight:  // Dock to right, shrink FAlignRect
      alClient: // Fill remaining FAlignRect
    end;
  end;
end;
----

=== TAnchors System

Defined in `src/corelib/fpg_main.pas`:

[source,pascal]
----
TAnchor = (anLeft, anRight, anTop, anBottom);
TAnchors = set of TAnchor;
----

Anchors work for widgets with `Align = alNone`. During parent resize, widgets maintain fixed distances to anchored edges. If both opposite edges are anchored (e.g., `[anLeft, anRight]`), the widget resizes to maintain both distances.

=== Limitations of Current System

1. **Limited Flexibility**: Only edge-based docking and anchoring
2. **No Relative Sizing**: Cannot size widgets as percentages of container
3. **No Grid Layouts**: Cannot create responsive grids
4. **No Flow Layouts**: Cannot wrap widgets automatically
5. **No Gap Management**: Manual spacing between widgets
6. **No Constraints**: Cannot express complex relationships (e.g., "same width as sibling")

== Java Swing LayoutManager Architecture

=== Core Concepts

Java Swing separates layout logic from container components through the `LayoutManager` interface:

[source,java]
----
public interface LayoutManager {
    void addLayoutComponent(String name, Component comp);
    void removeLayoutComponent(Component comp);
    Dimension preferredLayoutSize(Container parent);
    Dimension minimumLayoutSize(Container parent);
    void layoutContainer(Container parent);
}
----

**Key Features:**

* **Container delegates to LayoutManager**: Container calls `layoutContainer()` to position children
* **Constraints per widget**: Each widget can have layout-specific constraints
* **Size calculation**: Layout manager calculates preferred/minimum sizes
* **Pluggable**: Containers can change layout managers at runtime

=== MigLayout Overview

MigLayout is a powerful constraint-based layout manager that uses string-based constraints:

[source,java]
----
panel.setLayout(new MigLayout(
    "wrap 3",  // Layout constraints: 3-column grid with auto-wrap
    "[100]10[200]10[fill,grow]",  // Column constraints
    "[]10[]"   // Row constraints
));

panel.add(new JLabel("Name:"), "");
panel.add(nameField, "span 2, growx");  // Component constraints
panel.add(new JLabel("Address:"), "");
panel.add(addressField, "span 2, growx, wrap");
----

**MigLayout Features:**

* **Grid-based**: Implicit grid structure
* **Flexible constraints**: String-based constraint language
* **Relative sizing**: Percentage widths, grow factors
* **Gaps and alignment**: Built-in gap management
* **Spanning**: Widgets can span multiple grid cells
* **Docking**: Similar to fpGUI's Align but more flexible

== Proposed Architecture: ILayoutManager Interface

=== Design Goals

1. **Coexist with Align/Anchors**: Layout managers are optional; existing code works unchanged
2. **Zero runtime cost if unused**: No performance penalty for applications not using layout managers
3. **Pluggable**: Easy to implement custom layout managers using interfaces
4. **Constraint objects**: Type-safe, extensible constraint system
5. **Size negotiation**: Support preferred/minimum/maximum sizes
6. **Java Swing compatibility**: Follow Java's interface-based design pattern

==== ILayoutManager Interface

Core interface that all layout managers must implement (analogous to Java's `LayoutManager`):

[source,pascal]
----
type
  ILayoutManager = interface
    ['{3F2504E0-4F89-11D3-9A0C-0305E82C3301}']

    // Core layout methods
    procedure LayoutContainer(AContainer: TfpgWidget);
    function GetPreferredSize(AContainer: TfpgWidget): TfpgSize;
    function GetMinimumSize(AContainer: TfpgWidget): TfpgSize;

    // Constraint management
    procedure AddLayoutComponent(AWidget: TfpgWidget; AConstraint: TfpgLayoutConstraint);
    procedure RemoveLayoutComponent(AWidget: TfpgWidget);

    // Invalidation
    procedure InvalidateLayout(AContainer: TfpgWidget);
  end;
----

**Key Methods (matching Java's LayoutManager):**

* `LayoutContainer`: Position and size all child widgets (equivalent to Java's `layoutContainer`)
* `GetPreferredSize`: Calculate preferred size of container (equivalent to Java's `preferredLayoutSize`)
* `GetMinimumSize`: Calculate minimum size of container (equivalent to Java's `minimumLayoutSize`)
* `AddLayoutComponent`: Called when widget added with constraint (equivalent to Java's `addLayoutComponent`)
* `RemoveLayoutComponent`: Called when widget removed (equivalent to Java's `removeLayoutComponent`)
* `InvalidateLayout`: Mark layout as dirty, needs recalculation

**Purpose**: Provides common implementation for:

* Constraint storage in dictionary
* Layout invalidation and caching
* Default constraint creation
* Constraint lookup with automatic default creation

**Subclasses only need to implement:**

* `DoLayout`: The actual layout algorithm
* `DoGetPreferredSize`: Preferred size calculation
* `CreateDefaultConstraint`: Factory for constraint objects
* (Optional) `DoGetMinimumSize`: Minimum size calculation

==== Why Interface + Base Class Pattern?

**Advantages of Interface:**

1. **True pluggability**: Any class can implement `ILayoutManager`, not just descendants of a base class
2. **Multiple interfaces**: Classes could theoretically implement multiple layout behaviors
3. **Loose coupling**: Container only depends on interface, not implementation
4. **Java compatibility**: Mirrors Java Swing's design philosophy

**Advantages of Base Class:**

1. **Code reuse**: Common constraint management, caching, invalidation
2. **Convenience**: Most layout managers can extend `TfpgBaseLayoutManager`
3. **Reduces boilerplate**: Subclasses focus on layout algorithm, not infrastructure

**Best of Both Worlds:**

* Interface defines the contract
* Base class provides optional convenience implementation
* Advanced users can implement `ILayoutManager` directly if needed

==== Modified HandleAlignments

The key integration point - modify `HandleAlignments` to delegate to layout manager if present:

[source,pascal]
----
procedure TfpgWidget.HandleAlignments(const dwidth, dheight: TfpgCoord);
var
  alist: TList;
  n: integer;
  w: TfpgWidget;
begin
  // NEW: If this container has a layout manager, delegate to it
  if Assigned(FLayoutManager) then
  begin
    FLayoutManager.LayoutContainer(Self);  // Pass container to interface
    Exit;  // Layout manager handles everything
  end;

  // EXISTING: Original Align/Anchors logic
  FAlignRect := GetClientRect;
  alist := TList.Create;
  try
    for n := 0 to ComponentCount - 1 do
    begin
      w := TfpgWidget(Components[n]);
      if (w.Align <> alNone) and (w.Visible) then
        alist.Add(w);
    end;
    DoAlignment(alist);
  finally
    alist.Free;
  end;

  // Handle anchors...
end;
----

**Backward Compatibility**: If `FLayoutManager` is `nil`, the original Align/Anchors logic runs unchanged.

**Interface Usage**: Container passes `Self` to layout manager's `LayoutContainer` method, following the stateless interface pattern.

==== Component Notification

Integrate with TfpgWidget's component management to notify layout manager:

[source,pascal]
----
procedure TfpgWidget.Notification(AComponent: TComponent; Operation: TOperation);
begin
  inherited Notification(AComponent, Operation);

  // NEW: Notify layout manager of component changes
  if (Operation = opRemove) and (AComponent is TfpgWidget) and Assigned(FLayoutManager) then
  begin
    FLayoutManager.RemoveLayoutComponent(TfpgWidget(AComponent));
    FLayoutManager.InvalidateLayout(Self);
  end;
end;
----

**Purpose**: Automatically clean up constraint storage when widgets are removed.

=== Coexistence Strategy

The layout manager system **coexists** with Align/Anchors through a simple priority rule:

1. **If container has LayoutManager**: Use it, ignore Align/Anchors on children
2. **If container has no LayoutManager**: Use traditional Align/Anchors (current behavior)

**Per-Widget Behavior:**

* Widgets with `LayoutManager = nil` use Align/Anchors (default, backward compatible)
* Widgets with `LayoutManager` assigned use layout manager for their children

**Mixed Usage**: A widget can use a layout manager for its children while itself being positioned by its parent's Align/Anchors:

[source,pascal]
----
// Panel uses Align to dock to top
Panel.Align := alTop;
Panel.Height := 200;

// Panel's children use MigLayout
Panel.LayoutManager := TfpgMigLayoutManager.Create;
TfpgMigLayoutManager(Panel.LayoutManager).LayoutConstraints := 'wrap 3';
----


=== AddLayoutComponent vs. TfpgWidget Constructor

There might be some confusion here, and that is understandable and touches on a key design point. The AOwner
parameter in a widget's constructor establishes the parent-child ownership relationship, which is fundamental to
TComponent's memory management.

However, the layout manager introduces a parallel, but distinct, relationship for layout management.

* `TfpgWidget.Create(AOwner)`: This tells the widget "who owns it". The owner is responsible for freeing the
widget when the owner is destroyed. This is about object lifetime.

* `ILayoutManager.AddLayoutComponent(...)`: This tells the layout manager "I am a widget you need to manage, and
here are my specific layout rules". This is about object positioning and sizing.

The key reason we need AddLayoutComponent is to associate a widget with its layout constraint. The standard
Components array of a parent widget has no place to store this extra, layout-specific data (e.g., span 2, 
growx). The layout manager needs to maintain its own list or dictionary of the widgets it controls and their
corresponding constraints, as shown in the TfpgBaseLayoutManager implementation in the plan.

The example code for the MigLayout login form confirms this two-step process:
1. edtUsername := TfpgEdit.Create(Form); (Establishes ownership)
2. mig.AddLayoutComponent(edtUsername, mig.ParseComponentConstraint('growx')); (Establishes layout control and
provides constraints)

RemoveLayoutComponent is the necessary counterpart, ensuring that when a widget is removed from a container, the
layout manager also stops trying to manage it. This plan correctly specifies this should be called automatically
from TfpgWidget.Notification.

=== Not all TfpgWidgets are containers

We took the "Pragmatic" Approach in this plan. Add the property to the common base class (TfpgWidget). This makes
the property available on all widgets, even those that can't act as containers. The cost is minimal (a single
interface pointer per widget), and it simplifies the class structure. It relies on the developer to use the
feature correctly—only assigning a layout manager to a widget that will actually contain children.

==== Layout Algorithm (Simplified)

[source,pascal]
----
procedure TfpgMigLayoutManager.DoLayout(AContainer: TfpgWidget);
var
  grid: TfpgMigGrid;
  i, row, col: Integer;
  w: TfpgWidget;
  constraint: TfpgMigConstraint;
  cellRect: TfpgRect;
begin
  // 1. Build grid structure
  grid := TfpgMigGrid.Create(FColumnCount);
  try
    row := 0;
    col := 0;

    // Place widgets in grid cells
    for i := 0 to AContainer.ComponentCount - 1 do
    begin
      if AContainer.Components[i] is TfpgWidget then
      begin
        w := TfpgWidget(AContainer.Components[i]);
        if not w.Visible then
          Continue;

        constraint := GetConstraintOrDefault(w) as TfpgMigConstraint;

        // Add to grid
        grid.AddWidget(w, row, col, constraint.SpanX, constraint.SpanY);

        // Advance grid position
        Inc(col, constraint.SpanX);
        if col >= FColumnCount then
        begin
          col := 0;
          Inc(row);
        end;
      end;
    end;

    // 2. Calculate column widths and row heights
    grid.CalculateColumnWidths(AContainer.Width - LeftPadding - RightPadding, FColumnGap);
    grid.CalculateRowHeights(AContainer.Height - TopPadding - BottomPadding, FRowGap);

    // 3. Position widgets within cells
    for i := 0 to grid.CellCount - 1 do
    begin
      cellRect := grid.GetCellRect(i);
      w := grid.GetWidget(i);
      constraint := GetConstraintOrDefault(w) as TfpgMigConstraint;

      // Apply alignment and growth
      PositionWidgetInCell(w, cellRect, constraint);
    end;

  finally
    grid.Free;
  end;
end;
----

**Key Changes:**

* `AContainer` parameter: Container reference passed from interface method
* Uses `GetConstraintOrDefault`: Automatically creates default constraints if needed
* Stateless design: All state in `FColumnCount`, `FRowGap`, etc. - no stored container reference

===== Step 3: Column Width Calculation

This is the critical algorithm for distributing available space:

[source,pascal]
----
procedure TfpgMigGrid.CalculateColumnWidths(AAvailableWidth, AGap: Integer);
var
  i, cell_idx: Integer;
  cell: TfpgMigCell;
  totalGaps: Integer;
  remainingWidth: Integer;
  totalMinWidth: Integer;
  totalPrefWidth: Integer;
  growableColumns: TList<Integer>;
  totalGrowPriority: Integer;
  extraSpace: Integer;
begin
  // Initialize column dimensions
  SetLength(FColumns, FColumnCount);
  for i := 0 to FColumnCount - 1 do
  begin
    FColumns[i].MinSize := 0;
    FColumns[i].PrefSize := 0;
    FColumns[i].MaxSize := MaxInt;
    FColumns[i].GrowPriority := 0;
  end;

  // Phase 1: Calculate minimum and preferred sizes from widgets
  for cell_idx := 0 to FCells.Count - 1 do
  begin
    cell := FCells[cell_idx];

    // For single-column widgets, update column directly
    if cell.SpanX = 1 then
    begin
      // Get widget's preferred width
      if cell.Widget.PreferredWidth > 0 then
        FColumns[cell.Col].PrefSize := Max(FColumns[cell.Col].PrefSize,
                                            cell.Widget.PreferredWidth)
      else
        FColumns[cell.Col].PrefSize := Max(FColumns[cell.Col].PrefSize,
                                            cell.Widget.Width);

      // Get widget's minimum width
      if cell.Widget.MinWidth > 0 then
        FColumns[cell.Col].MinSize := Max(FColumns[cell.Col].MinSize,
                                          cell.Widget.MinWidth)
      else
        FColumns[cell.Col].MinSize := Max(FColumns[cell.Col].MinSize, 20); // default min

      // Check if column should grow
      if cell.Constraint.GrowX then
        FColumns[cell.Col].GrowPriority := Max(FColumns[cell.Col].GrowPriority, 100);
    end;
    // For multi-column widgets, distribute size across spanned columns
    // (More complex algorithm - omitted for brevity, but would proportionally
    //  distribute widget's preferred size across spanned columns)
  end;

  // Phase 2: Calculate total required width
  totalGaps := (FColumnCount - 1) * AGap;
  totalMinWidth := totalGaps;
  totalPrefWidth := totalGaps;

  for i := 0 to FColumnCount - 1 do
  begin
    totalMinWidth := totalMinWidth + FColumns[i].MinSize;
    totalPrefWidth := totalPrefWidth + FColumns[i].PrefSize;
  end;

  // Phase 3: Distribute available width
  remainingWidth := AAvailableWidth - totalGaps;

  if remainingWidth <= totalMinWidth then
  begin
    // Not enough space - use minimum sizes (may cause clipping)
    for i := 0 to FColumnCount - 1 do
      FColumns[i].Size := FColumns[i].MinSize;
  end
  else if remainingWidth <= totalPrefWidth then
  begin
    // Between min and preferred - scale proportionally
    for i := 0 to FColumnCount - 1 do
    begin
      if totalPrefWidth > 0 then
        FColumns[i].Size := FColumns[i].MinSize +
          Round((FColumns[i].PrefSize - FColumns[i].MinSize) *
                (remainingWidth - totalMinWidth) / (totalPrefWidth - totalMinWidth))
      else
        FColumns[i].Size := remainingWidth div FColumnCount;
    end;
  end
  else
  begin
    // More than preferred - grow columns with GrowPriority
    growableColumns := TList<Integer>.Create;
    try
      totalGrowPriority := 0;

      // Start with preferred sizes
      for i := 0 to FColumnCount - 1 do
      begin
        FColumns[i].Size := FColumns[i].PrefSize;
        if FColumns[i].GrowPriority > 0 then
        begin
          growableColumns.Add(i);
          totalGrowPriority := totalGrowPriority + FColumns[i].GrowPriority;
        end;
      end;

      // Distribute extra space to growable columns
      extraSpace := remainingWidth - totalPrefWidth;

      if (growableColumns.Count > 0) and (totalGrowPriority > 0) then
      begin
        for i in growableColumns do
        begin
          FColumns[i].Size := FColumns[i].Size +
            Round(extraSpace * FColumns[i].GrowPriority / totalGrowPriority);
        end;
      end;

    finally
      growableColumns.Free;
    end;
  end;

  // Phase 4: Calculate column positions
  FColumns[0].Position := 0;
  for i := 1 to FColumnCount - 1 do

function TfpgMigGrid.GetCellRect(ACell: TfpgMigCell): TfpgRect;
var
  i: Integer;
  totalWidth, totalHeight: Integer;
begin
  // Calculate total width of spanned columns
  totalWidth := 0;
  for i := ACell.Col to ACell.Col + ACell.SpanX - 1 do
  begin
    totalWidth := totalWidth + FColumns[i].Size;
    if i < ACell.Col + ACell.SpanX - 1 then
      totalWidth := totalWidth + FColumnGap;  // Add gaps between columns
  end;

  // Calculate total height of spanned rows
  totalHeight := 0;
  for i := ACell.Row to ACell.Row + ACell.SpanY - 1 do
  begin
    totalHeight := totalHeight + FRows[i].Size;
    if i < ACell.Row + ACell.SpanY - 1 then
      totalHeight := totalHeight + FRowGap;  // Add gaps between rows
  end;

  // Set cell rectangle
  Result.SetRect(
    FColumns[ACell.Col].Position,
    FRows[ACell.Row].Position,
    totalWidth,
    totalHeight

===== Step 6: Applying Alignment and Growth

[source,pascal]
----
procedure TfpgMigLayoutManager.PositionWidgetInCell(AWidget: TfpgWidget;
  const ACellRect: TfpgRect; AConstraint: TfpgMigConstraint);
var
  widgetRect: TfpgRect;
  widgetWidth, widgetHeight: Integer;
begin
  widgetRect := ACellRect;

  // Calculate widget width based on constraint
  case AConstraint.AlignX of
    maFill:
      widgetWidth := ACellRect.Width;  // Fill entire cell width
    else
      // Use preferred width or current width
      if AWidget.PreferredWidth > 0 then
        widgetWidth := AWidget.PreferredWidth
      else
        widgetWidth := AWidget.Width;

      // Apply horizontal alignment
      case AConstraint.AlignX of
        maLeft:
          widgetRect.Left := ACellRect.Left;
        maCenter:
          widgetRect.Left := ACellRect.Left + (ACellRect.Width - widgetWidth) div 2;
        maRight:
          widgetRect.Left := ACellRect.Right - widgetWidth;
      end;

      widgetRect.Width := widgetWidth;
  end;

  // Calculate widget height based on constraint (similar to width)
  case AConstraint.AlignY of
    maFill:
      widgetHeight := ACellRect.Height;
    else
      if AWidget.PreferredHeight > 0 then
        widgetHeight := AWidget.PreferredHeight
      else
        widgetHeight := AWidget.Height;

      case AConstraint.AlignY of
        maTop:
          widgetRect.Top := ACellRect.Top;
        maCenter:
          widgetRect.Top := ACellRect.Top + (ACellRect.Height - widgetHeight) div 2;
        maBottom:
          widgetRect.Top := ACellRect.Bottom - widgetHeight;
      end;

      widgetRect.Height := widgetHeight;
  end;

  // Apply calculated bounds to widget
  AWidget.SetPosition(widgetRect.Left, widgetRect.Top, widgetRect.Width, widgetRect.Height);
end;
----

===== Complete DoLayout with All Steps

[source,pascal]
----
procedure TfpgMigLayoutManager.DoLayout(AContainer: TfpgWidget);
var
  grid: TfpgMigGrid;
  i, row, col: Integer;
  w: TfpgWidget;
  constraint: TfpgMigConstraint;
  cellRect: TfpgRect;
  cell: TfpgMigCell;
  containerRect: TfpgRect;
  availWidth, availHeight: Integer;
begin
  // Get container's client area
  containerRect := AContainer.GetClientRect;

  // Account for padding
  availWidth := containerRect.Width - FPaddingLeft - FPaddingRight;
  availHeight := containerRect.Height - FPaddingTop - FPaddingBottom;

  // Create grid structure
  grid := TfpgMigGrid.Create(FColumnCount);
  try
    row := 0;
    col := 0;

    // STEP 1: Build grid and place widgets in cells
    for i := 0 to AContainer.ComponentCount - 1 do
    begin
      if AContainer.Components[i] is TfpgWidget then
      begin
        w := TfpgWidget(AContainer.Components[i]);
        if not w.Visible then
          Continue;  // Skip invisible widgets

        constraint := GetConstraintOrDefault(w) as TfpgMigConstraint;

        // Add widget to grid at current position
        grid.AddWidget(w, row, col, constraint.SpanX, constraint.SpanY, constraint);

        // Advance to next grid position
        Inc(col, constraint.SpanX);
        if col >= FColumnCount then
        begin
          col := 0;
          Inc(row);
        end;
      end;
    end;

    // STEP 2: Calculate column widths
    // This distributes available width across columns based on:
    // - Widget preferred/minimum widths
    // - Growth priorities
    // - Available space
    grid.CalculateColumnWidths(availWidth, FColumnGap);

    // STEP 3: Calculate row heights
    // Similar to column calculation, but for vertical dimension
    grid.CalculateRowHeights(availHeight, FRowGap);

    // STEP 4: Position and size each widget
    for i := 0 to grid.CellCount - 1 do
    begin
      cell := grid.GetCell(i);

      // Get the rectangle for this cell (accounting for spans)
      cellRect := grid.GetCellRect(cell);

      // Offset by container padding
      cellRect.Left := cellRect.Left + FPaddingLeft;
      cellRect.Top := cellRect.Top + FPaddingTop;

      // Position widget within cell based on alignment constraints
      PositionWidgetInCell(cell.Widget, cellRect, cell.Constraint);
    end;

  finally
    grid.Free;
  end;
end;
----

===== Key Algorithms Explained

**Column Width Distribution Algorithm:**

1. **Phase 1 - Measure**: Calculate min/pref sizes from all widgets
2. **Phase 2 - Check Available Space**:
   - If `available < totalMin`: Use minimum sizes (widgets may clip)
   - If `totalMin <= available <= totalPref`: Scale proportionally between min and pref
   - If `available > totalPref`: Use preferred sizes, distribute extra to growable columns
3. **Phase 3 - Growth Distribution**: Extra space distributed proportionally by GrowPriority
4. **Phase 4 - Position**: Calculate absolute positions from accumulated sizes

**Widget Positioning Algorithm:**

1. Calculate cell bounds from grid (handling spans)
2. Apply widget's alignment within cell:
   - `Fill`: Widget fills entire cell
   - `Left/Top`: Widget at start of cell with preferred size
   - `Center`: Widget centered in cell with preferred size
   - `Right/Bottom`: Widget at end of cell with preferred size
3. Set widget bounds using `SetPosition`

**Time Complexity:**

- Column/Row calculation: O(n) where n = number of widgets
- Widget positioning: O(n)
- Overall: O(n) - linear in number of widgets

   - Add layout manager support to codebase
   - Existing applications continue using Align/Anchors
   - Zero impact on existing code

2. **Phase 2: New Code**
   - New forms/dialogs use layout managers
   - Existing forms unchanged
   - Mixed approach in same application

   - Migrate complex forms to layout managers
   - Keep simple forms with Align/Anchors

   - Recommend layout managers for new projects

**Use Layout Managers When:**

* Creating forms with many controls

* Complex grid layouts
* Need consistent spacing/gaps
* Localization (text expansion)
* Dynamic UI (adding/removing controls)

**Use Align/Anchors When:**

* Simple docking scenarios (toolbar, statusbar)
* Fixed-size dialogs
* Single control in container
* Legacy code maintenance
* Performance-critical scenarios

**Align/Anchors will NOT be deprecated**. Both systems will coexist indefinitely because:

2. **Simplicity**: Align/Anchors is simpler for basic layouts
3. **Performance**: Zero overhead for simple cases
4. **Learning Curve**: New users can start with Align/Anchors

  TfpgBaseLayoutManager = class(TInterfacedObject, ILayoutManager)

  FLayoutDirty := True;

== Interface Design: Key Benefits

==== 1. True Separation of Concerns

Interface references in Object Pascal are automatically reference counted:

[source,pascal]

Panel.LayoutManager := TfpgMigLayoutManager.Create;  // Ref count = 1
// When Panel destroyed, interface ref count decrements

No need for manual memory management!

6. **Allows gradual adoption** without forcing rewrites
7. **Leverages automatic reference counting** for clean memory management

The interface-based approach provides maximum flexibility while the `TfpgBaseLayoutManager` helper class ensures convenience for common implementations.
