== Executive Summary

This document specifies how HVIF vector icons are integrated into the fpGUI
framework and applications built with it. It covers four concerns:

. *Embedding* — compiling HVIF data into executables without shipping external
  files, using two complementary strategies (Pascal `const` arrays for framework
  standard images, pre-compiled `.res` files for application-specific icons).
. *Icon store* — a new `TfpgIconStore` class that holds HVIF vector sources
  alongside legacy bitmap entries, keyed by the same string identifiers the
  framework already uses.
. *DPI-aware rendering* — a model where widgets request icons at a logical
  size, the store computes the physical pixel size from the current screen DPI,
  and HVIF icons are rendered on demand at the correct resolution.
. *Widget integration* — minimal changes to existing widgets so that the
  string-based `ImageName` property transparently resolves HVIF icons through
  the new store with a fallback to the legacy `fpgImages` bitmap store.

The design draws on practices from Qt's `QIcon` / `QIconEngine` architecture
and Haiku OS's `BIconUtils` system API, adapted to fpGUI's existing patterns
and constraints.


== Prior Work

This document builds on link:icon_format_analysis.adoc[fpGUI Icon Format
Analysis], which selected HVIF as the embedded shipping format and defined the
reader (`fpg_hvif.pas`), writer (`fpg_hvif_writer.pas`), and SVG-to-HVIF
converter (`svg2hvif`). The reader is implemented and tested. The writer and
converter are implemented. This document addresses the next layer: how the
framework and applications consume HVIF icons at runtime.


== How Other Frameworks Handle This

Understanding how mature toolkits solve the same problem informs the design
choices below.

=== Qt

Qt's icon system separates the _source_ of an icon from its _rendered
representation_:

* `QIcon` is a handle that can hold multiple sources — SVG files, pixmaps at
  various sizes, or a custom `QIconEngine` subclass.
* When a widget paints an icon, it calls `QIcon::paint(painter, rect, ...)`.
  Internally, Qt picks the best source for the current _device pixel ratio_
  and renders at the physical pixel size. A 24×24 logical icon on a 2× HiDPI
  display renders at 48×48 physical pixels.
* `QSvgIconEngine` re-rasterises SVG on demand at the requested size. This is
  conceptually identical to what `THvifIcon.GetImage(w, h)` does.
* `QIcon::fromTheme("document-open")` looks up icons by string name from the
  freedesktop.org icon theme, supporting named icon lookup at the system level.
* Qt caches rendered pixmaps internally, keyed by (size, mode, state).

The relevant principles for fpGUI:

. Separate logical icon size from physical render size.
. Let the icon source (vector data) bridge the gap — the widget never knows
  whether the underlying source is bitmap or vector.
. Cache rendered bitmaps keyed by pixel dimensions.

=== Haiku OS

Haiku takes the most direct approach: the operating system itself owns icon
rendering.

* HVIF data is stored in filesystem extended attributes (BFS) or as binary
  resources inside application binaries.
* Applications never render icons directly. They call
  `BIconUtils::GetVectorIcon(data, dataSize, bitmap, iconSize)` — pass the raw
  HVIF bytes and desired pixel size, receive a rasterised `BBitmap`.
* The Tracker (file manager), Deskbar, and all standard controls call
  `BIconUtils` with whatever size they need. There is no concept of "this icon
  is 16px" — icons are resolution-independent by design.
* Toolbar widgets (`BToolBar`) request icons at the current UI scale factor
  automatically.

The relevant principles for fpGUI:

. Icons are identified by name or resource key, not by pixel dimensions.
. Rasterisation is on-demand, driven by the rendering context's required size.
. The same icon data serves every size — no multi-resolution asset bundles.


== Embedding Strategy

fpGUI applications must not require external `.hvif` files at runtime. Two
complementary embedding mechanisms are used, chosen by the nature of the
icon set.

=== Strategy A: Pascal `const` Byte Arrays (Framework Standard Images)

This is the existing pattern used by `stdimages.inc`, where BMP image data
is stored as Pascal `const` arrays compiled directly into the unit. A build
tool converts `.hvif` binary files into Pascal source:

[source,pascal]
----
(* Generated by hvif2inc — do not edit *)
const
  hvif_stdimg_quit: array[0..523] of Byte = (
    $6E, $63, $69, $66, ...
  );

  hvif_stdimg_save: array[0..487] of Byte = (
    $6E, $63, $69, $66, ...
  );
----

A new include file `stdhvifimages.inc` holds these declarations, referenced
from a new unit `fpg_stdicons.pas`.

[cols="2,3", options="header"]
|===
| Property | Value

| Platform support
| All platforms — no toolchain dependency

| Build complexity
| None — `.inc` file is checked into source control

| Binary overhead
| Negligible — hex encoding adds ~1 byte per source byte vs raw binary, but
  icons average 500–700 bytes each

| Maintenance
| Run `hvif2inc` once per icon change, commit the updated `.inc`

| When to use
| Framework standard images (`stdimg.*`, `sys.*`)
|===

=== Strategy B: Pre-compiled `.res` Files (Application-Specific Icons)

For applications with many icons (the IDE, for example), a `.res` resource file
is compiled from a `.rc` manifest using FPC's `fpcres` tool and checked into the
repository. The application references it with `{$R filename.res}`.

The IDE already uses this pattern:

[source,pascal]
----
(* ide.form.main.pas *)
{$R ide.main.res}
----

[source]
----
(* ide.main.rc *)
MYAPP_ICON_BUILD  RCDATA  "icons/build.hvif"
MYAPP_ICON_DIFF   RCDATA  "icons/diff.hvif"
----

At startup the application loads each resource into the icon store:

[source,pascal]
----
fpgIcons.RegisterFromResource(HInstance, 'MYAPP_ICON_BUILD', 'ide.build');
fpgIcons.RegisterFromResource(HInstance, 'MYAPP_ICON_DIFF',  'ide.diff');
----

[cols="2,3", options="header"]
|===
| Property | Value

| Platform support
| All platforms — `fpcres` is shipped with FPC and compiles `.rc` to `.res`
  in a platform-neutral binary format

| Build complexity
| One manual or scripted step: `fpcres -o ide.main.res ide.main.rc`

| Binary overhead
| Minimal — raw HVIF bytes stored directly in the resource section

| Maintenance
| Add `.hvif` file to icons directory, add line to `.rc`, recompile `.res`

| When to use
| Application-specific icons (IDE, uidesigner, examples)
|===

=== Why Not Automatic `.rc` Compilation?

FPC's `{$R somefile.rc}` directive only triggers automatic compilation to `.res`
on Windows (via `windres`). On Linux and macOS, FPC expects the pre-compiled
`.res` file to exist. FPC ships `fpcres` which can compile `.rc` files on any
platform, but the compiler does not invoke it automatically when it encounters
a `{$R}` directive referencing an `.rc` file.

Rather than fighting the build system, the design accepts a one-time manual
step and documents it. This is the same approach used by Lazarus projects that
target multiple platforms.


== Icon Store Architecture

=== Design Goals

. Preserve the existing string-identifier pattern (`ImageName := 'stdimg.quit'`)
  — no API change for widget consumers.
. Support mixed bitmap and HVIF entries in the same store.
. Render HVIF icons on demand at the physical pixel size determined by the
  current screen DPI.
. Cache rendered images to avoid redundant rasterisation.
. Provide a clear DPI change hook (application restart acceptable for v1).

=== Class Design

[source,pascal]
----
unit fpg_iconstore;

{$mode objfpc}{$H+}

interface

uses
  Classes, SysUtils,
  fpg_base, fpg_main, fpg_hvif;

type

  { Describes the source type of an icon entry }
  TfpgIconSourceKind = (iskBitmap, iskHVIF);


  { A single entry in the icon store. Holds either an HVIF vector source
    or a legacy bitmap image, and manages the rendered image cache for
    HVIF entries. }
  TfpgIconEntry = class
  private
    FKind: TfpgIconSourceKind;
    FHvifIcon: THvifIcon;         (* owned — nil for bitmap entries *)
    FBitmapIcon: TfpgImage;       (* not owned — reference to fpgImages entry *)
  public
    destructor Destroy; override;
    property Kind: TfpgIconSourceKind read FKind;
  end;


  { TfpgIconStore — the central registry for named icons.

    Holds HVIF vector sources and legacy bitmap references. Renders HVIF
    icons on demand at the requested pixel size, using THvifIcon's internal
    image cache.

    String identifiers follow the same naming convention as fpgImages:
      'stdimg.quit', 'stdimg.save', 'ide.build', etc.

    Thread safety: NOT thread-safe. Use from the fpGUI main thread only. }
  TfpgIconStore = class
  private
    FEntries: TStringList;         (* sorted, owns TfpgIconEntry objects *)
    FDefaultSize: Integer;         (* current default icon size in pixels *)
    FDesignedDPI: Integer;         (* DPI at which logical sizes are defined *)
    FCurrentDPI: Integer;          (* actual screen DPI *)
    function  FindEntry(const AId: string): TfpgIconEntry;
    function  ComputePhysicalSize(ALogicalSize: Integer): Integer;
  public
    constructor Create;
    destructor Destroy; override;

    { Registration — HVIF sources }
    procedure RegisterHVIF(const AId: string;
                           AData: PByte; ADataSize: Integer);
    procedure RegisterFromStream(const AId: string; AStream: TStream);
    procedure RegisterFromResource(AInstance: THandle;
                                   const AResName: string;
                                   const AId: string);

    { Registration — legacy bitmap fallback }
    procedure RegisterBitmap(const AId: string; AImage: TfpgImage);

    { Retrieval — returns a rendered TfpgImage at the given pixel size.
      For HVIF entries, renders on demand and caches the result.
      For bitmap entries, returns the bitmap at its native size regardless
      of ASize.
      Returns nil if the identifier is not registered. }
    function GetIcon(const AId: string;
                     ASize: Integer): TfpgImage;

    { Retrieval — returns a rendered TfpgImage at the default size
      (computed from FCurrentDPI and a 16px logical base). }
    function GetIcon(const AId: string): TfpgImage;

    { DPI management.
      Call once at application startup. Computes FDefaultSize from the
      screen DPI and the designed DPI (default 96).
      For v1, DPI changes require an application restart. }
    procedure SetDPI(AScreenDPI: Integer);

    { Invalidates all cached rendered images. Call after SetDPI or when
      the application needs to force re-rendering (e.g. theme change). }
    procedure InvalidateCache;

    { Queries }
    function HasIcon(const AId: string): Boolean;
    procedure ListIcons(out AList: TStringList);

    property DefaultSize: Integer read FDefaultSize;
    property CurrentDPI: Integer read FCurrentDPI;
    property DesignedDPI: Integer read FDesignedDPI write FDesignedDPI;
  end;

----

=== DPI-to-Size Calculation

The store computes the physical pixel size for icons using the ratio between
the actual screen DPI and the designed DPI (the DPI at which the application's
layout was authored — typically 96):

[source,pascal]
----
function TfpgIconStore.ComputePhysicalSize(ALogicalSize: Integer): Integer;
begin
  if FCurrentDPI <= 0 then
    Result := ALogicalSize
  else
    Result := Round(ALogicalSize * FCurrentDPI / FDesignedDPI);
  (* Clamp to at least 8px to prevent degenerate renders *)
  if Result < 8 then
    Result := 8;
end;
----

Example values for a 16px logical icon:

[cols="2,1,1", options="header"]
|===
| Screen DPI | Scale factor | Physical size (pixels)

| 96 (standard)
| 1.0×
| 16

| 120 (125%)
| 1.25×
| 20

| 144 (150%)
| 1.5×
| 24

| 192 (200%)
| 2.0×
| 32
|===

For toolbar icons (typically 24px logical), the same calculation yields 24, 30,
36, and 48 pixels respectively.

=== Image Cache Lifecycle

HVIF image caching is managed by `THvifIcon` internally (as defined in
`fpg_hvif.pas`). Each `THvifIcon` instance maintains an array of
`THvifCachedImage` records keyed by (Width, Height). The cache lifecycle is:

. *First request* at a given size: `THvifIcon.GetImage(w, h)` renders into a
  new `TfpgImage`, stores it in the cache, and returns it.
. *Subsequent requests* at the same size: cache hit, no rendering.
. *DPI change*: `TfpgIconStore.InvalidateCache` destroys all `THvifIcon`
  instances and re-creates them from the stored HVIF byte data. This clears
  all cached images. The next `GetIcon` call renders at the new size.
. *Shutdown*: `TfpgIconStore.Destroy` frees all `TfpgIconEntry` objects,
  which free their `THvifIcon` instances, which free all cached images.

The practical cache size is small — a given icon is typically rendered at 1–3
sizes (e.g. 16px for menus, 24px for toolbars, 32px for dialogs). The linear
scan in `THvifIcon.FindCachedImage` is appropriate for this scale.


== Widget Integration

=== Current Flow

Today, a widget resolves an icon as follows:

[source]
----
TfpgBaseButton.SetImageName(AValue)
  → FImage := fpgImages.GetImage(FImageName)
  → Canvas.DrawImage(x, y, FImage)
----

`fpgImages.GetImage` returns a `TfpgImage` at whatever fixed size was
registered during `fpgCreateStandardImages`. There is no size negotiation
and no DPI awareness.

=== Proposed Flow

The widget resolution adds a single check before falling back to the legacy
store:

[source]
----
TfpgBaseButton.SetImageName(AValue)
  → FImage := fpgIcons.GetIcon(FImageName, FIconSize)
  → if FImage = nil then
      FImage := fpgImages.GetImage(FImageName)    (* legacy fallback *)
  → Canvas.DrawImage(x, y, FImage)
----

The change in each widget's `SetImageName` (or equivalent) method is minimal:

[source,pascal]
----
procedure TfpgBaseButton.SetImageName(const AValue: string);
begin
  FImageName := AValue;
  if Assigned(fpgIcons) then
    FImage := fpgIcons.GetIcon(FImageName, FIconSize);
  if FImage = nil then
    FImage := fpgImages.GetImage(FImageName);
  Repaint;
end;
----

Where `FIconSize` is the widget's logical icon size (defaulting to 16 for
menu items, 24 for toolbar buttons, 32 for dialog icons). Widgets that
already know their preferred icon size expose it as a property; widgets that
do not can use the store's `DefaultSize`.

=== Widgets Requiring Changes

The following widgets and framework components use `fpgImages.GetImage` with
a string identifier and require the fallback-to-`fpgIcons` change:

[cols="2,3", options="header"]
|===
| Unit / class | Usage

| `fpg_button.pas` / `TfpgBaseButton`
| `SetImageName` → toolbar and dialog button icons

| `fpg_tree.pas` / `TfpgTreeView`
| Node icons via `ImageIndex` → `TfpgImageList`

| `fpg_listview.pas` / `TfpgListView`
| Item icons

| `fpg_grid.pas` / `TfpgStringGrid`
| Cell icons

| `fpg_editbtn.pas` / `TfpgEditButton`
| Embedded button icon

| `fpg_scrollbar.pas`
| Arrow icons (`sys.sb.up`, etc.)

| `fpg_popupcalendar.pas`
| Navigation arrow icons

| `fpg_main.pas` / `TfpgStyle.DrawMenuItemImage`
| Menu check mark and submenu arrow

| `fpg_form.pas`
| System menu icon
|===

The `TfpgImageList` class (used by `TfpgTreeView`) is index-based rather
than name-based. For v1, `TfpgImageList` is unchanged — it continues to
hold `TfpgImage` references. Applications that want HVIF tree node icons
can populate the image list with pre-rendered images from the icon store:

[source,pascal]
----
imgList.AddImage(fpgIcons.GetIcon('ide.folder_src', 16), 0);
imgList.AddImage(fpgIcons.GetIcon('ide.file_pas', 16), 1);
----

=== Backwards Compatibility

The design is fully backwards-compatible:

* `fpgImages` continues to exist and function as before.
* Widgets that are not updated continue to use `fpgImages` exclusively.
* Applications that register no HVIF icons see no behaviour change.
* The `fpgIcons` global variable is created during `fpgApplication`
  initialisation, alongside `fpgImages`.
* Legacy BMP icons registered in `fpgImages` are not duplicated in
  `fpgIcons` unless explicitly registered there.


== Framework Initialisation Sequence

The icon store is created and populated during fpGUI's application
initialisation, after `fpgImages` and before the main form:

[source,pascal]
----
(* fpg_main.pas — initialisation section *)
fpgImages := TfpgImages.Create;
fpgCreateStandardImages;          (* legacy BMP standard images *)

fpgIcons := TfpgIconStore.Create;
fpgIcons.SetDPI(fpgApplication.Screen_dpi);
fpgCreateStandardIcons;           (* HVIF standard icons *)
----

`fpgCreateStandardIcons` is defined in the new `fpg_stdicons.pas` unit:

[source,pascal]
----
unit fpg_stdicons;

{$I fpg_defines.inc}

interface

uses
  fpg_iconstore;

procedure fpgCreateStandardIcons;

implementation

{$I stdhvifimages.inc}

procedure fpgCreateStandardIcons;
begin
  fpgIcons.RegisterHVIF('stdimg.quit',
      @hvif_stdimg_quit, SizeOf(hvif_stdimg_quit));
  fpgIcons.RegisterHVIF('stdimg.save',
      @hvif_stdimg_save, SizeOf(hvif_stdimg_save));
  fpgIcons.RegisterHVIF('stdimg.open',
      @hvif_stdimg_open, SizeOf(hvif_stdimg_open));
  (* ... one call per standard icon ... *)
end;

end.
----

=== Migration Path for Standard Images

Standard images are migrated from BMP to HVIF incrementally:

. Convert an existing BMP icon's SVG source to HVIF using `svg2hvif`.
. Run `hvif2inc` to generate the Pascal `const` array.
. Add the entry to `stdhvifimages.inc` and register it in
  `fpgCreateStandardIcons`.
. The icon is now available from both `fpgIcons` (HVIF, scalable) and
  `fpgImages` (legacy BMP, fixed size). Widgets updated to check `fpgIcons`
  first will get the HVIF version; unchanged widgets continue using the BMP.

Once all widgets are updated and all standard icons have HVIF equivalents,
the BMP versions in `stdimages.inc` can be removed (major version bump).


== DPI Change Handling

=== Version 1: Application Restart

For v1, DPI changes require an application restart. The rationale is:

* Haiku OS also requires an application restart for icon scale changes.
* Runtime DPI changes affect far more than icons (font sizes, widget layouts,
  spacing) — a full solution is a separate project.
* The icon store's `SetDPI` / `InvalidateCache` mechanism is designed to
  support runtime changes, but the widget repaint coordination is out of scope
  for this design.

The v1 flow:

. Application starts. `fpgApplication.Screen_dpi` returns the current DPI.
. `fpgIcons.SetDPI(fpgApplication.Screen_dpi)` computes `FDefaultSize`.
. All subsequent `GetIcon` calls render at the correct physical size.
. If the user changes the desktop DPI/scaling, they restart the application.

=== Version 2: Runtime DPI Response (Future)

A future version can support runtime DPI changes by:

. Detecting the DPI change event from the platform layer (X11 `Xft.dpi`
  resource change, GDI `WM_DPICHANGED` message, Cocoa
  `NSWindowDidChangeBackingPropertiesNotification`).
. Calling `fpgIcons.SetDPI(newDPI)` followed by `fpgIcons.InvalidateCache`.
. Broadcasting a framework-level `DPIChanged` event that widgets listen to
  in order to re-query their icon and trigger a repaint.

The icon store architecture supports this without structural changes — only
the event wiring and widget response logic need to be added.


== IDE-Specific Integration

The IDE (Maximus) has its own icon set beyond the framework standard images.
These are compiled into a `.res` file using Strategy B.

=== Current State

The IDE already has:

* `ide/src/main/resources/ide.main.rc` — resource manifest
* `ide/src/main/resources/icons/*.hvif` — HVIF icon files (build, diff,
  folder_src, readme, release, search, settings, todo, xml)
* `ide/src/main/pascal/ide.form.main.pas` — `{$R ide.main.res}`

=== Startup Registration

The IDE's main form startup registers its icons with the store:

[source,pascal]
----
procedure TMainForm.RegisterIdeIcons;
begin
  fpgIcons.RegisterFromResource(HInstance, 'MYAPP_ICON_BUILD',  'ide.build');
  fpgIcons.RegisterFromResource(HInstance, 'MYAPP_ICON_DIFF',   'ide.diff');
  (* ... etc ... *)
end;
----

Toolbar buttons then use the standard `ImageName` property:

[source,pascal]
----
btnBuild.ImageName := 'ide.build';
----

=== Adding New IDE Icons

The workflow for adding a new icon to the IDE:

. Create or obtain an SVG source file.
. Convert to HVIF: `svg2hvif icons/newicon.svg`
. Add to the resource manifest: `MYAPP_ICON_NEWICON RCDATA "icons/newicon.hvif"`
. Recompile the resource: `fpcres -o ide.main.res ide.main.rc`
. Register in `RegisterIdeIcons`:
  `fpgIcons.RegisterFromResource(HInstance, 'MYAPP_ICON_NEWICON', 'ide.newicon');`
. Use in the form: `btnNewAction.ImageName := 'ide.newicon';`


== Build Tooling

Two small command-line tools support the workflow:

=== `hvif2inc` — HVIF to Pascal Include File Generator

Converts one or more `.hvif` binary files into a Pascal `const` array
declaration suitable for inclusion in an `.inc` file.

[source]
----
Usage:
  hvif2inc [options] input.hvif [input2.hvif ...]

Options:
  -o <file>       Output .inc file (default: stdout)
  -p <prefix>     Const name prefix (default: "hvif_")
  --append        Append to output file instead of overwriting

Examples:
  hvif2inc -o stdhvifimages.inc -p hvif_stdimg_ icons/*.hvif
  hvif2inc icons/quit.hvif  →  stdout: hvif_quit: array[0..N] of Byte = (...)
----

This tool is trivial (~100 LOC) — it reads binary files and writes hex-encoded
Pascal `const` arrays.

=== `svg2hvif` — SVG to HVIF Converter

Already defined in the analysis document. Converts SVG files to HVIF binary
format.

== Summary of Design Decisions

[cols="2,3,2", options="header"]
|===
| Decision | Rationale | Alternative considered

| Pascal `const` arrays for framework icons
| Matches existing `stdimages.inc` pattern; zero build-system complexity;
  works on all platforms
| `.res` for everything — rejected because it adds a mandatory build step
  to the framework itself

| `.res` files for application icons
| Cleaner for large icon sets; raw binary storage is more compact;
  IDE already uses this pattern
| `const` arrays for everything — viable but verbose for 50+ icons

| New `TfpgIconStore` alongside `fpgImages`
| Full backwards compatibility; legacy BMP icons keep working; incremental
  migration
| Replace `TfpgImages` — rejected due to breaking change risk

| Widgets check `fpgIcons` then fall back to `fpgImages`
| One-line change per widget; transparent to application code; icons can be
  migrated from BMP to HVIF without touching application code
| Merge stores into one — rejected because `TfpgImages` has a different
  ownership model (it owns `TfpgImage` instances) and serves non-icon
  purposes (checkbox sprites, radio button sprites)

| DPI via `ComputePhysicalSize(logicalSize * screenDPI / designedDPI)`
| Matches Qt's device pixel ratio model; uses fpGUI's existing `DesignedDPI`
  property; simple and predictable
| Fixed scale factors (1×, 1.5×, 2×) — rejected because it creates gaps and
  the continuous calculation is equally simple

| Application restart for DPI changes (v1)
| Runtime DPI response affects the entire widget tree, not just icons; Haiku
  also requires restart; the icon store architecture supports future runtime
  changes without modification
| Runtime DPI response — deferred to v2

| `hvif2inc` as a separate tool
| Keeps the build workflow explicit and auditable; the generated `.inc` is
  checked into source control so builds are reproducible without running the
  tool
| Inline generation at compile time — not possible in FPC
|===


== Open Questions

. *Icon size per widget class:* Should `TfpgBaseButton` default to 16px or
  24px logical? Toolbar buttons typically use 24px; dialog buttons use 16px.
  Should this be a property on the widget or derived from context?

. *Naming convention for IDE icons:* The current `.rc` uses `MYAPP_ICON_BUILD`
  as the resource name and `ide.build` as the store identifier. Should there be
  a formal convention (e.g. `app.category.name`)?

. *Legacy icon removal timeline:* When can BMP entries in `stdimages.inc` be
  removed? This should be gated on all widgets being updated to check
  `fpgIcons` first, and a major version bump of the framework.

. *Multi-monitor DPI:* fpGUI's `TfpgScreenInfo` already carries per-monitor
  DPI values. Should the icon store support per-monitor DPI (rendering icons
  at different sizes on different monitors)? This is a v2+ concern but the
  store's `GetIcon(id, size)` overload already supports it — the widget
  just needs to pass the correct monitor's DPI-adjusted size.
