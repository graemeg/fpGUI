= UI Toolkit Sizing API Comparison
:toc: left
:sectnums:

== Executive Summary

All major UI toolkits (Swing, Qt, WPF, SWT, GTK+) implement a clear separation between **intent** (preferred/desired size) and **result** (actual size). This separation is fundamental to robust layout management and is considered industry best practice.

.Common Pattern Across All Toolkits
|===
| Concept | Purpose | Set By | Read By

| **Intent/Preferred Size**
| What size the widget wants to be
| Developer or widget's content calculation
| Layout manager

| **Actual Size**
| What size the widget currently is after layout
| Layout manager
| Developer (for reading only)

| **Constraints**
| Min/max boundaries
| Developer
| Layout manager
|===

== Framework-by-Framework Analysis

=== Java Swing (est. 1997)

==== Intent Properties

* `getPreferredSize()` / `setPreferredSize(Dimension)`
* `getMinimumSize()` / `setMinimumSize(Dimension)`
* `getMaximumSize()` / `setMaximumSize(Dimension)`

==== Result Properties

* `getSize()` / `setSize(int, int)`
* `getBounds()` / `setBounds(Rectangle)`

==== Key Principles

**Separation of concerns**: Layout managers read preferred sizes, then call `setSize()` to apply the calculated result. Developers should call `setPreferredSize()` to express intent, not `setSize()`.

**Expert guidance**: "setSize() should be thought of as something that the layout manager calls - not something that you call." (Stack Overflow community consensus)

**Backward compatibility**: Both APIs exist, but `setSize()` is only appropriate for components without layout managers (rare in modern Swing).

**Method calling**: Custom widgets override `getPreferredSize()` to calculate based on content. Framework calls this during layout.

=== Qt (C++, est. 1995)

==== Intent Properties

* `sizeHint()` - returns QSize with preferred dimensions
* `minimumSizeHint()` - returns QSize with minimum preferred dimensions
* `setSizePolicy(QSizePolicy)` - controls how widget responds to available space

==== Result Properties

* `size()` - returns QSize with actual dimensions
* `geometry()` - returns QRect with position and size
* `resize(int, int)` / `setGeometry(QRect)` - sets actual size

==== Key Principles

**Virtual method override**: Custom widgets override `sizeHint()` and `minimumSizeHint()` virtual methods to provide their preferred dimensions.

**Automatic constraint enforcement**: "The size component is adjusted if it lies outside the range defined by minimumSize() and maximumSize()."

**Layout manager contract**: "QLayout will never resize a widget to a size smaller than the minimum size hint unless minimumSize() is set or the size policy is set to QSizePolicy::Ignore."

**Event-based notification**: When layout calls `resize()` or `setGeometry()`, widget receives `resizeEvent()` notification.

=== WPF (C#/.NET, est. 2006)

==== Intent Properties

* `Width` / `Height` - input properties (can be set but don't reflect actual size)
* `MinWidth` / `MinHeight` / `MaxWidth` / `MaxHeight` - constraints
* `DesiredSize` - calculated during Measure pass (read-only)

==== Result Properties

* `ActualWidth` / `ActualHeight` - read-only properties with actual rendered size
* `RenderSize` - the final render size after layout

==== Key Principles

**Two-pass layout system**:

1. **Measure Pass**: Parent calls `Measure(Size constraint)` on children, which calculates `DesiredSize` based on content and constraints
2. **Arrange Pass**: Parent calls `Arrange(Rect bounds)` on children, which sets `ActualWidth`/`ActualHeight`

**Explicit read-only enforcement**: `ActualWidth` and `ActualHeight` have no setters - they are truly read-only properties calculated by the layout system.

**Clear documentation**: "ActualHeight is a calculated value based on other height inputs and the layout system."

**Virtual method overrides**: Custom controls override `MeasureOverride(Size)` to calculate desired size and `ArrangeOverride(Size)` to finalize layout.

**Important distinction**: Setting `Width` doesn't guarantee `ActualWidth` will match - the layout system makes the final decision.

=== Eclipse SWT (Java, est. 2000)

==== Intent Properties

* `computeSize(int wHint, int hHint)` - calculates preferred size given optional width/height hints
* `computeSize(int wHint, int hHint, boolean changed)` - with cache invalidation

==== Result Properties

* `getSize()` - returns Point with current size
* `setSize(int, int)` / `setSize(Point)` - sets actual size
* `getBounds()` / `setBounds(Rectangle)` - position and size

==== Key Principles

**Hint-based calculation**: `computeSize()` can answer questions like "Given width of 200px, how tall should I be?" by passing hints. Use `SWT.DEFAULT` for unconstrained dimension.

**Layout manager usage**: Layout managers call `computeSize()` to determine preferred dimensions, then call `setSize()` to apply calculated size.

**Content-driven sizing**: Default implementation calculates size based on widget's content (text, children, etc.).

**Common pattern**:

[source,java]
----
Point size = control.computeSize(SWT.DEFAULT, SWT.DEFAULT);
control.setSize(size);
----

=== GTK+ (C/GObject, est. 1998)

==== Intent Properties

* `gtk_widget_get_preferred_width()` - gets minimum and natural width
* `gtk_widget_get_preferred_height()` - gets minimum and natural height
* `gtk_widget_get_preferred_size()` - gets both as GtkRequisition
* `gtk_widget_set_size_request()` - sets minimum size constraint

==== Result Properties

* `gtk_widget_get_allocated_width()` / `gtk_widget_get_allocated_height()` - actual allocated size
* `gtk_widget_size_allocate()` - called by parent to set actual size
* `size-allocate` signal - emitted when widget receives new allocation

==== Key Principles

**Two-pass system similar to WPF**:

1. **Size Request**: Bottom-up, widgets report minimum and natural sizes
2. **Size Allocation**: Top-down, containers allocate actual sizes to children

**Virtual methods**: Custom widgets override `get_preferred_width_vfunc` and `get_preferred_height_vfunc` to provide their preferred dimensions.

**Height-for-width support**: Can query preferred height given a specific width, supporting text widgets that reflow.

**Signal-based monitoring**: Use `size-allocate` signal to detect when widget receives new actual size.

**Important note**: "There's a difference between what size a widget would like to have and what size it actually gets."

== Common Design Patterns

All five frameworks share these fundamental patterns:

=== Clear Method Name Distinction

Every framework uses different names for intent vs result:

|===
| Framework | Intent Method | Result Method

| Swing | `getPreferredSize()` | `getSize()`
| Qt | `sizeHint()` | `size()`
| WPF | `DesiredSize` (calculated) | `ActualWidth`/`ActualHeight`
| SWT | `computeSize()` | `getSize()`
| GTK+ | `get_preferred_size()` | `get_allocated_width/height()`
|===

The naming makes it **impossible to confuse** intent with result.

=== Virtual Methods for Custom Widgets

All frameworks expect custom widgets to override methods that calculate preferred size:

|===
| Framework | Override Method

| Swing | `getPreferredSize()`
| Qt | `sizeHint()`, `minimumSizeHint()`
| WPF | `MeasureOverride(Size)`
| SWT | `computeSize(int, int, boolean)`
| GTK+ | `get_preferred_width_vfunc()`, `get_preferred_height_vfunc()`
|===

=== Layout Manager as the Authority

In all frameworks:

1. **Developer** expresses intent (preferred size, constraints)
2. **Layout manager** reads intent from all children
3. **Layout manager** calculates actual sizes based on available space, constraints, and layout rules
4. **Layout manager** applies results by calling size-setting methods
5. **Widget** receives notification (event, signal, or override) of final size

=== Constraints as Boundaries

All frameworks support min/max constraints that act as hard boundaries:

* **Swing**: `getMinimumSize()`, `getMaximumSize()`
* **Qt**: `minimumSize()`, `maximumSize()`, `minimumSizeHint()`
* **WPF**: `MinWidth`, `MinHeight`, `MaxWidth`, `MaxHeight`
* **SWT**: Less formal, but `computeSize()` hints can enforce constraints
* **GTK+**: `set_size_request()` sets minimum size

=== Read-Only Result Properties

Most modern frameworks make actual size read-only:

* **WPF**: `ActualWidth`/`ActualHeight` have no public setters
* **GTK+**: `get_allocated_width()` is read-only; only layout system calls `size_allocate()`
* **Qt**: `size()` is read-only; use `resize()` method to change it
* **Swing/SWT**: Both readable, but convention is that only layout managers should call setters

== What Nobody Does

No major framework exhibits these anti-patterns:

❌ **Using a single property for both intent and result** - Everyone separates these concepts

❌ **Allowing developers to directly set actual size in layout-managed contexts** - Result is always controlled by layout system

❌ **Making preferred size read-only** - Intent must be settable by developers

❌ **Returning current size as preferred size when none is set** - This creates feedback loops

❌ **Ambiguous property names** - Names clearly indicate whether it's intent or result

== Implications for fpGUI's Proposed Design

=== Strong Industry Validation

The proposed separation of `PreferredSize` (intent) from `Width`/`Height` (result) aligns with 25+ years of industry best practices across five major frameworks.

=== Naming Recommendations

Based on industry standards, consider:

|===
| Current Proposal | Industry Standard Alternative | Rationale

| `PreferredSize` (R/W)
| ✓ Good - matches Swing, GTK+
| Clear intent indication

| `Width`/`Height` (Read-only)
| Consider `ActualWidth`/`ActualHeight`
| WPF's naming makes read-only nature explicit

| `SetWidth()`/`SetHeight()`
| Potentially confusing
| If Width is "read-only", why does SetWidth() exist?
|===

=== The Backward Compatibility Challenge

The proposal's approach of redirecting `SetWidth()` to modify `PreferredSize` has **no precedent** in the surveyed frameworks. Here's why:

**WPF's approach**:

* `Width` property IS settable (input property)
* `ActualWidth` property is truly read-only (output property)
* No confusion because they're different properties with different names

**Qt's approach**:

* `resize(w, h)` method exists and is callable
* BUT it's documented that layout managers will override it
* Developers are warned not to use it in layout-managed contexts

**Swing's approach**:

* Both `setSize()` and `setPreferredSize()` exist
* Community convention: only use `setSize()` for non-layout-managed components
* No magic redirection

=== The Read-After-Write Problem

The proposed design creates this surprising behavior:

[source,pascal]
----
widget.Width := 100;        // Actually sets FPreferredSize.W := 100
x := widget.Width;          // Returns FWidth (current actual size)
// x might not be 100!
----

**No surveyed framework exhibits this behavior.** They solve it in two ways:

1. **Different property names** (WPF: `Width` vs `ActualWidth`)
2. **Both properties readable and writable** but with strong conventions (Swing, Qt)

=== Better Alternative: Follow WPF's Model

==== The Solution

[source,pascal]
----
// Unified preferred size storage with flexible property access
private
  FPreferredSize: TfpgSize;  // Unified storage
  FWidth: TfpgCoord;         // Actual width
  FHeight: TfpgCoord;        // Actual height

public
  property PreferredSize: TfpgSize read FPreferredSize write SetPreferredSize;
  property ActualSize: TfpgSize read GetActualSize;

  property ActualWidth: TfpgCoord read FWidth;   // Truly read-only, no setter
  property ActualHeight: TfpgCoord read FHeight; // Truly read-only, no setter

  // Keep Width/Height as legacy properties that work with preferred size
  property Width: TfpgCoord read GetWidth write SetWidth;    // Maps to FPreferredSize.W
  property Height: TfpgCoord read GetHeight write SetHeight; // Maps to FPreferredSize.H
----

==== How This Solves Read-After-Write

**The Problem** (original proposal):

[source,pascal]
----
// Original proposal: Width getter returns FWidth (actual), setter modifies FPreferredSize
button.Width := 200;        // Sets FPreferredSize.W := 200
                            // But FWidth still has old value (e.g., 150)

x := button.Width;          // Returns FWidth = 150 (NOT 200!)
// SURPRISE! You just set Width to 200, but reading it gives 150
----

**The Solution** (WPF-inspired model with unified storage):

[source,pascal]
----
// Both getter and setter work with the SAME backing field (FPreferredSize.W)
button.Width := 200;              // Sets FPreferredSize.W := 200
x := button.Width;                // Returns FPreferredSize.W = 200 ✓
// No surprise! Read-after-write is consistent

// If you want the actual size after layout, use the explicit property
actual := button.ActualWidth;     // Returns FWidth (might be different than 200)
----

==== Complete Example

[source,pascal]
----
// Setting up a button before layout
myButton := TfpgButton.Create(self);
myButton.Text := 'Click Me';
myButton.Width := 200;            // Sets preferred width
myButton.Height := 30;            // Sets preferred height

WriteLn('Requested: ', myButton.Width, 'x', myButton.Height);
// Output: "Requested: 200x30"  ✓ Consistent with what we set

WriteLn('Actual (before layout): ', myButton.ActualWidth, 'x', myButton.ActualHeight);
// Output: "Actual (before layout): 10x10"  (default initial values)

// ... Layout manager runs ...
// Layout gives button only 150 pixels width due to space constraints

WriteLn('Requested: ', myButton.Width, 'x', myButton.Height);
// Output: "Requested: 200x30"  ✓ Intent preserved

WriteLn('Actual (after layout): ', myButton.ActualWidth, 'x', myButton.ActualHeight);
// Output: "Actual (after layout): 150x30"  ← What layout actually gave it

// Developer can check if they got what they wanted
if myButton.ActualWidth < myButton.Width then
  WriteLn('Warning: Button was constrained smaller than requested');
----

==== Benefits

* ✓ **Read-after-write consistency**: `Width := 200` then `x := Width` gives `x = 200`
* ✓ **Clear API**: `ActualWidth` explicitly means "result after layout"
* ✓ **Backward compatible**: Old code using `Width`/`Height` continues to work without changes
* ✓ **Intent preserved**: Layout system can't accidentally overwrite developer's desired size
* ✓ **Familiar to developers**: Matches WPF, the most modern of the surveyed frameworks

== Key Takeaways

1. **Industry consensus**: Intent/result separation is universal and proven over 25+ years

2. **Naming matters**: Clear, distinct names prevent confusion (e.g., `DesiredSize` vs `ActualWidth`)

3. **Virtual methods**: Custom widgets calculate preferred size by overriding methods

4. **Layout manager authority**: Result size is always set by layout system, never directly by developer

5. **Constraints are boundaries**: Min/max properties are respected by all layout systems

6. **No magic redirects**: No framework redirects `SetWidth()` to mean `SetPreferredWidth()` - they use different names or clear conventions

7. **Read-only enforcement**: Modern frameworks (WPF, GTK+) make actual size truly read-only with no setter

== Recommendation

=== Proposed API Design

**Follow WPF's model with fpGUI naming conventions, using unified preferred size storage**:

[source,pascal]
----
// In TfpgWidgetBase:
private
  FPreferredSize: TfpgSize;  // Unified storage for preferred dimensions
  FWidth: TfpgCoord;         // Actual width after layout
  FHeight: TfpgCoord;        // Actual height after layout

  function GetWidth: TfpgCoord;
  function GetHeight: TfpgCoord;
  function GetActualSize: TfpgSize;
  procedure SetWidth(const AValue: TfpgCoord);
  procedure SetHeight(const AValue: TfpgCoord);
  procedure SetPreferredSize(const AValue: TfpgSize);

public
  // Aggregate properties
  property PreferredSize: TfpgSize read FPreferredSize write SetPreferredSize;
  property ActualSize: TfpgSize read GetActualSize;

  // Individual properties - for intent (backward compatible)
  property Width: TfpgCoord read GetWidth write SetWidth;
  property Height: TfpgCoord read GetHeight write SetHeight;

  // Individual properties - for result (new, read-only)
  property ActualWidth: TfpgCoord read FWidth;
  property ActualHeight: TfpgCoord read FHeight;
----

=== Design Rationale

==== Why Unified FPreferredSize Storage?

**Preferred size is conceptually a single unit** - it represents the widget's desired dimensions as a cohesive whole. When a button calculates its preferred size, it's thinking "I need 120×30 pixels", not "I need width 120" and separately "I need height 30". The dimensions are interdependent.

**Benefits**:

* ✓ **Semantic clarity**: Matches how widgets naturally think about their desired size
* ✓ **Atomic updates**: Can set both dimensions in one operation
* ✓ **Clean API for calculation**: `DoCalculatePreferredSize(var ASize: TfpgSize)` works with single parameter
* ✓ **Flexibility**: Supports both aggregate (`PreferredSize`) and individual (`Width`/`Height`) access patterns

==== Why Both Aggregate and Individual Properties?

**Different properties suit different use cases**:

**Aggregate properties** (`PreferredSize`, `ActualSize`):

* Setting a widget's desired size: `button.PreferredSize := TfpgSize.Create(200, 30);`
* Comparing sizes: `if widget1.ActualSize = widget2.ActualSize then...`
* Saving/restoring state: `savedSize := widget.ActualSize;`

**Individual properties** (`Width`, `Height`, `ActualWidth`, `ActualHeight`):

* Reading in layout calculations: `if w.ActualWidth > availableSpace then...`
* Painting code: `Canvas.DrawRectangle(0, 0, ActualWidth, ActualHeight);`
* Conditional logic: `if ActualWidth < Width then ShowScrollbar;`
* Performance-critical paths: Direct field access instead of function calls

**Industry precedent**: All major frameworks (WPF, Qt, Swing, GTK+) provide BOTH aggregate and individual access to actual size. Individual properties are used far more frequently in practice.

==== Property Implementation Details

[source,pascal]
----
// Width/Height getters return preferred size (for backward compatibility)
function TfpgWidgetBase.GetWidth: TfpgCoord;
begin
  Result := FPreferredSize.W;
end;

function TfpgWidgetBase.GetHeight: TfpgCoord;
begin
  Result := FPreferredSize.H;
end;

// Width/Height setters modify preferred size
procedure TfpgWidgetBase.SetWidth(const AValue: TfpgCoord);
begin
  if FPreferredSize.W <> AValue then
  begin
    FPreferredSize.W := AValue;

    // Also set actual width if not in layout-managed context (backward compatibility)
    if not Assigned(Parent) or not Assigned(Parent.LayoutManager) then
      HandleResize(AValue, FHeight);

    DoPreferredSizeChanged;
  end;
end;

// ActualSize aggregate constructs record from actual dimensions
function TfpgWidgetBase.GetActualSize: TfpgSize;
begin
  Result.W := FWidth;
  Result.H := FHeight;
end;

// PreferredSize setter is atomic
procedure TfpgWidgetBase.SetPreferredSize(const AValue: TfpgSize);
begin
  if (FPreferredSize.W <> AValue.W) or (FPreferredSize.H <> AValue.H) then
  begin
    FPreferredSize := AValue;

    // Also set actual size if not in layout-managed context (backward compatibility)
    if not Assigned(Parent) or not Assigned(Parent.LayoutManager) then
      HandleResize(AValue.W, AValue.H);

    DoPreferredSizeChanged;
  end;
end;
----

=== How This Solves Read-After-Write

**Key insight**: Both the getter AND setter of `Width` work with the **same backing field** (`FPreferredSize.W`), ensuring consistency:

[source,pascal]
----
// Developer code - completely intuitive behavior
button.Width := 200;                    // Sets FPreferredSize.W := 200
w := button.Width;                      // Returns FPreferredSize.W = 200 ✓
// No surprise! You get back what you set

// Alternative: set both dimensions at once
button.PreferredSize := TfpgSize.Create(200, 30);  // Sets FPreferredSize atomically

// When you need the actual size after layout runs
actualW := button.ActualWidth;          // Returns FWidth (what layout gave it)
actualSize := button.ActualSize;        // Returns TfpgSize(FWidth, FHeight)

// Layout manager code
procedure TfpgMigLayoutManager.TransferBounds(...);
begin
  // Layout reads the intent (can use Width property or PreferredSize.W)
  preferredW := widget.Width;           // Returns FPreferredSize.W
  // or
  preferredSize := widget.PreferredSize;  // Returns FPreferredSize record

  // Layout calculates actual size based on constraints and available space
  calculatedW := CalculateSize(preferredW, constraints, availableSpace);

  // Layout sets the result via internal method (NOT via Width property!)
  widget.HandleResize(calculatedW, calculatedH);  // Sets FWidth, FHeight directly
end;
----

=== Why This Works

1. **Developer reads/writes intent**: Using `Width` property always works with `FPreferredSize.W`
2. **Layout reads intent**: Layout manager reads `Width` (returns `FPreferredSize.W`) or `PreferredSize` (returns entire record)
3. **Layout writes result**: Layout calls `HandleResize()` which modifies `FWidth`/`FHeight` directly
4. **Developer reads result**: Using `ActualWidth` property reads the final `FWidth`, or `ActualSize` for both dimensions
5. **No confusion**: Intent and result are stored in different fields, accessed via different properties

=== Benefits

* ✓ **Read-after-write consistency**: Setting then reading `Width` gives back the same value
* ✓ **Aligns with industry best practices**: Matches WPF's clear separation
* ✓ **Backward compatible**: Existing code using `Width`/`Height` continues to work unchanged
* ✓ **Clear, unambiguous API**: New code can use explicit `PreferredSize`/`ActualSize` or `ActualWidth`/`ActualHeight`
* ✓ **Prevents layout feedback loops**: Layout result doesn't overwrite developer's intent
* ✓ **Familiar to developers**: Anyone who has used WPF will immediately understand this pattern
* ✓ **Flexible access patterns**: Both aggregate and individual properties available for all use cases

== Compatibility with Anchors and Align

=== The Critical Question

**Will this design work when layout managers are NOT used, and developers continue using Anchors and Align as they always have?**

**Answer: YES**, this design works perfectly for both layout managers AND the traditional Anchor/Align system. The key insight is that both are forms of "layout logic" that follow the same contract.

=== How Anchors and Align Currently Work

In fpGUI today, the `HandleAlignments` method in `TfpgWidget` manages both Align properties and Anchors:

1. **Parent container's resize event triggers**
2. **`HandleAlignments` is called** with delta width/height
3. **For Align properties** (alTop, alBottom, alLeft, alRight, alClient):
   - Logic reads child's current actual width/height: `w.Width`, `w.Height`
   - Calculates new position and size based on alignment rules
   - Calls `w.MoveAndResize(left, top, width, height)` to apply changes
4. **For Anchors** (when Align = alNone):
   - Calculates position/size deltas based on anchor flags
   - Calls `w.MoveAndResizeBy(dx, dy, dw, dh)` → `MoveAndResize(...)` to apply changes
5. **`MoveAndResize` calls `HandleResize(width, height)`**
6. **`HandleResize` directly modifies `FWidth` and `FHeight`** (actual size fields)

=== The Problem with Current Implementation

**Current code in `DoAlignment` method** (fpg_widget.pas):

[source,pascal]
----
alTop:
  begin
    w.MoveAndResize(FAlignRect.Left, FAlignRect.Top, FAlignRect.Width, w.Height);
    //                                                                  ^^^^^^^^
    //                                                    Reads actual size from w.Height
    Inc(FAlignRect.top, w.Height);
    Dec(FAlignRect.Height, w.Height);
  end;

alLeft:
  begin
    w.MoveAndResize(FAlignRect.Left, FAlignRect.Top, w.Width, FAlignRect.Height);
    //                                               ^^^^^^^
    //                                    Reads actual size from w.Width
    Inc(FAlignRect.Left, w.Width);
    Dec(FAlignRect.Width, w.Width);
  end;
----

If we change `Width`/`Height` properties to return `FPreferredSize.W`/`FPreferredSize.H` without any other changes, **this alignment code would read the wrong value** and produce incorrect layouts.

=== The Solution: Use ActualWidth/ActualHeight for Reading

The fix is simple and surgical - update `HandleAlignments` to read from the explicit actual size properties:

**Updated code in `DoAlignment` method**:

[source,pascal]
----
alTop:
  begin
    w.MoveAndResize(FAlignRect.Left, FAlignRect.Top, FAlignRect.Width, w.ActualHeight);
    //                                                                  ^^^^^^^^^^^^^
    //                                                        Now reads actual size explicitly
    Inc(FAlignRect.top, w.ActualHeight);
    Dec(FAlignRect.Height, w.ActualHeight);
  end;

alBottom:
  begin
    w.MoveAndResize(FAlignRect.Left, FAlignRect.Top + FAlignRect.Height - w.ActualHeight,
                    FAlignRect.Width, w.ActualHeight);
    Dec(FAlignRect.Height, w.ActualHeight);
  end;

alLeft:
  begin
    w.MoveAndResize(FAlignRect.Left, FAlignRect.Top, w.ActualWidth, FAlignRect.Height);
    //                                               ^^^^^^^^^^^^
    //                                     Now reads actual size explicitly
    Inc(FAlignRect.Left, w.ActualWidth);
    Dec(FAlignRect.Width, w.ActualWidth);
  end;

alRight:
  begin
    w.MoveAndResize(FAlignRect.Left + FAlignRect.Width - w.ActualWidth, FAlignRect.Top,
                    w.ActualWidth, FAlignRect.Height);
    Dec(FAlignRect.Width, w.ActualWidth);
  end;

alClient:
  w.MoveAndResize(FAlignRect.Left, FAlignRect.Top, FAlignRect.Width, FAlignRect.Height);
  // Note: alClient doesn't read child size, so no change needed
----

=== Why This Works

The key architectural insight is that **`HandleResize()` is an internal method that bypasses the property setters**:

**Public API (for developers and external code)**:

* `PreferredSize` property: getter returns `FPreferredSize`, setter modifies `FPreferredSize`
* `ActualSize` property: getter returns `TfpgSize(FWidth, FHeight)` (read-only, no setter)
* `Width` property: getter returns `FPreferredSize.W`, setter modifies `FPreferredSize.W`
* `Height` property: getter returns `FPreferredSize.H`, setter modifies `FPreferredSize.H`
* `ActualWidth` property: getter returns `FWidth` (read-only, no setter)
* `ActualHeight` property: getter returns `FHeight` (read-only, no setter)

**Internal API (for layout logic - both layout managers AND anchor/align)**:

* `HandleResize(w, h)`: **Directly modifies `FWidth` and `FHeight`** (bypasses property setters)
* This is the method that layout logic (including anchors/align) uses to set actual size

**Flow for Anchor/Align system**:

[source,pascal]
----
procedure TfpgWidget.HandleAlignments(const dwidth, dheight: TfpgCoord);
begin
  // ... process Align properties ...
  for each aligned widget w do
  begin
    // 1. Read the actual current size
    currentWidth := w.ActualWidth;   // Returns FWidth
    currentHeight := w.ActualHeight; // Returns FHeight

    // 2. Calculate new size based on alignment rules
    newWidth := CalculateAlignedWidth(...);
    newHeight := CalculateAlignedHeight(...);

    // 3. Apply via MoveAndResize (which calls HandleResize internally)
    w.MoveAndResize(newLeft, newTop, newWidth, newHeight);
    //                                 ↓
    //                          calls HandleResize(newWidth, newHeight)
    //                                 ↓
    //                     directly sets FWidth := newWidth, FHeight := newHeight
  end;
end;
----

**Flow for Anchor system** (already correct, no changes needed):

[source,pascal]
----
// For widgets with Anchors set
if (anRight in wg.Anchors) then
  if (anLeft in wg.Anchors) then
    dw := dwidth  // Anchored both sides → grow width by parent's delta
  else
    dx := dwidth  // Anchored right only → move right by parent's delta

// Apply the calculated deltas
wg.MoveAndResizeBy(dx, dy, dw, dh);
//        ↓
// calls MoveAndResize(FLeft + dx, FTop + dy, FWidth + dw, FHeight + dh)
//        ↓
// calls HandleResize(newWidth, newHeight)
//        ↓
// directly sets FWidth := newWidth, FHeight := newHeight
----

Note that the anchor code uses `FWidth` and `FHeight` internally (line 1825 in `MoveAndResizeBy`), which is correct because it's reading actual size in an internal method.

=== Unified Layout Contract

This design creates a **single, unified sizing contract** that works for ALL forms of layout:

[cols="1,2,2", options="header"]
|===
| Layout System | Reads Actual Size From | Sets Actual Size Via

| **Layout Managers**
| `widget.ActualWidth`, `widget.ActualHeight`
| `widget.HandleResize(w, h)` internally

| **Align Properties**
| `widget.ActualWidth`, `widget.ActualHeight`
| `widget.MoveAndResize(...)` → `HandleResize(w, h)` internally

| **Anchors**
| Internal fields `FWidth`, `FHeight` in `MoveAndResizeBy`
| `widget.MoveAndResize(...)` → `HandleResize(w, h)` internally

| **Manual Positioning** (no layout system)
| `widget.ActualWidth`, `widget.ActualHeight` (if needed)
| `widget.Width := value` (sets preferred size, then call `UpdateLayout` if needed)
|===

=== Benefits for Anchor/Align System

1. **✓ Clear separation of concerns**: Layout logic (including anchors/align) reads actual size, calculates new size, sets actual size via internal methods
2. **✓ No feedback loops**: Parent resize → calculate new child size based on actual current size → set new actual size
3. **✓ Consistent with layout managers**: Both systems use the same contract
4. **✓ Preserves developer intent**: If developer sets `Width := 200`, that preference is preserved in `FPreferredSize.W` even after layout modifies actual width
5. **✓ Backward compatible**: Existing code works with minimal changes (just read from `ActualWidth`/`ActualHeight` instead of `Width`/`Height` in layout calculations)

=== Complete Example: Widget with Align Property

[source,pascal]
----
// Create a panel with Align = alTop
panel := TfpgPanel.Create(Form1);
panel.Align := alTop;
panel.Height := 50;  // Sets FPreferredSize.H := 50

// What happens during layout?

// 1. Form's HandleAlignments is called
// 2. DoAlignment processes the panel:
actualH := panel.ActualHeight;  // Returns FHeight (current actual height)
//                                   First time, this might be 10 (default initial value)

// 3. Alignment logic says: "alTop means use preferred height"
panel.MoveAndResize(0, 0, Form1.ClientWidth, panel.Height);
//                                            ^^^^^^^^^^^^
//                                    Reads FPreferredSize.H = 50 ← WAIT, this is wrong!

// CORRECTION: We should NOT read panel.Height here!
// The alignment logic should use a separate variable or read ActualHeight first, then
// decide whether to honor preferred size or calculate based on content.

// Actually, looking at the code, alTop DOES read w.Height:
//   w.MoveAndResize(FAlignRect.Left, FAlignRect.Top, FAlignRect.Width, w.Height);
//
// This means: "Keep the widget's current height, but stretch width to fill alignment rect"
// So we DO need ActualHeight here!

// 4. Corrected flow:
panel.MoveAndResize(0, 0, Form1.ClientWidth, panel.ActualHeight);
//                                            ^^^^^^^^^^^^^^^^^^^
//                                            Returns FHeight (actual current height)

// 5. But wait - how does the panel get its preferred height of 50?
// Answer: The first time panel is shown, its initial size should be set to preferred size!
----

**Important realization**: There's a subtle issue here. When a widget with `Align = alTop` and `Height := 50` is added to a form, how does it get its initial height of 50?

**Answer**: The widget's **initial actual size** should be set to its **preferred size** when it's first added to the parent. This happens in the widget's initialization or when it's added to a parent. After that, the align logic preserves that height.

**Updated understanding**:

[source,pascal]
----
// When widget is added to parent or shown for first time
procedure TfpgWidget.AfterConstruction;
begin
  inherited;
  // If preferred size is set, use it as initial actual size
  if (FPreferredSize.W > 0) or (FPreferredSize.H > 0) then
  begin
    if FPreferredSize.W > 0 then
      FWidth := FPreferredSize.W;
    if FPreferredSize.H > 0 then
      FHeight := FPreferredSize.H;
  end;
end;
----

**Alternative**: The `SetPreferredSize` (and `SetWidth`/`SetHeight` when they modify preferred size) should ALSO set the actual size if the widget hasn't been laid out yet:

[source,pascal]
----
procedure TfpgWidgetBase.SetWidth(const AValue: TfpgCoord);
begin
  // Set preferred width
  if FPreferredSize.W <> AValue then
  begin
    FPreferredSize.W := AValue;

    // If widget hasn't been laid out yet (or no layout manager), also set actual width
    if not Assigned(Parent) or not Assigned(Parent.LayoutManager) then
      HandleResize(AValue, FHeight);

    DoPreferredSizeChanged;
  end;
end;
----

This ensures backward compatibility: `panel.Height := 50` both sets preferred height AND actual height (if not in a layout-managed context).

=== Final Architecture Summary

**For widgets WITHOUT layout managers** (using Align/Anchors):

1. Developer sets `Width := 200` → Sets `FPreferredSize.W := 200` AND `FWidth := 200` (if not in layout-managed context)
2. Parent resizes → `HandleAlignments` called
3. Alignment logic reads `w.ActualWidth` to get current size
4. Alignment logic calculates new size based on rules
5. Alignment logic calls `w.MoveAndResize(...)` → `HandleResize(...)` to set new actual size
6. `FWidth` and `FHeight` updated to new actual size
7. Developer can check `ActualWidth` to see what layout actually gave the widget
8. Developer's original intent (`FPreferredSize.W := 200`) is preserved and not overwritten

**For widgets WITH layout managers**:

1. Developer sets `Width := 200` → Sets `FPreferredSize.W := 200` (actual size NOT modified)
2. Parent resizes → `HandleAlignments` → delegates to layout manager
3. Layout manager reads `w.Width` (returns `FPreferredSize.W`) or `w.PreferredSize.W` to get developer's intent
4. Layout manager calculates actual size based on constraints, available space, etc.
5. Layout manager calls `w.HandleResize(...)` to set actual size
6. `FWidth` and `FHeight` updated to calculated actual size
7. Developer can check `ActualWidth` to see what layout actually gave the widget
8. Developer's original intent (`FPreferredSize.W := 200`) is preserved and not overwritten

Both systems work harmoniously with the same API!

== Migration Guide: Fixing Width/Height Usage

=== Overview

After implementing the intent vs actual size separation (where `Width`/`Height` properties now return `FPreferredSize` instead of `FWidth`/`FHeight`), ALL code that needs actual rendered dimensions must be updated to use `ActualWidth`/`ActualHeight` instead.

**Critical insight**: This is a widespread breaking change that affects nearly every part of the framework that reads widget dimensions for:

* Rendering/painting operations
* Hit-testing (mouse clicks, bounds checking)
* Layout calculations
* Size calculations
* Visibility checks

=== Critical Fix: SetWidth/SetHeight Backward Compatibility

**FIXED**: `SetWidth`/`SetHeight` now properly support manual positioning without layout managers.

The original implementation only set actual size during construction (`csLoading` check), which broke code like:

[source,pascal]
----
lblTitle := TfpgLabel.Create(self);
lblTitle.SetPosition(20, 12, 240, 30);  // Actual size never set - stayed 10x10!
----

**Solution**: Changed from `csLoading` check to layout manager check:

[source,pascal]
----
// OLD (broken for manual positioning):
if (csLoading in ComponentState) then
  FWidth := AValue;

// NEW (works for both):
if not Assigned(Parent) or not Assigned(Parent.LayoutManager) then
  FWidth := AValue;
----

This ensures:
- Manual positioning (SetPosition) sets actual size ✓
- Layout managers override via HandleResize ✓
- Backward compatibility maintained ✓

**Status**: ✓ FIXED in fpg_base.pas:1757-1758 (SetWidth) and 1742-1743 (SetHeight)

**Important**: Not all `.Width`/`.Height` reads need changing! Only change them if the code needs **actual rendered size** rather than **preferred size**.

**When to keep Width/Height**:

* Layout managers reading widget's **intent** (what size it wants)
* Code that needs to **preserve developer's desired size**
* Align properties reading child's preferred dimension

**When to change to ActualWidth/ActualHeight**:

* Painting/rendering operations
* Hit-testing (mouse events, bounds checking)
* Container reading its own size for layout
* Visibility/clipping calculations
* Native window sizing
