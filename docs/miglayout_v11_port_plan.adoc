== Executive Summary

This document outlines the plan to port MigLayout v11.4.2 from Java to Object Pascal for fpGUI. Rather than continuing test-driven development from scratch, we will systematically port the battle-tested Java implementation while preserving the fpGUI-native architecture we've already established.

**Source:** `prototypes/miglayout/mig-java-latest/` (MigLayout v11.4.2 for Java)

**Branch:** `feature/miglayout-v11-port`

**Key Strategy:**

* Port proven v11.4.2 algorithms while keeping fpGUI architecture
* **API-first approach**: Full fluent API first, string parser deferred to Phase 2
* **Test-as-you-go**: Write tests alongside each class for immediate validation
* Reuse existing `ILayoutManager` interface and base classes
* Leverage existing unit tests as regression validation
* Build confidence incrementally - catch bugs early
* Gain 11 versions worth of bug fixes and features
* Native HiDPI support via logic units
* Use interfaces and generics where beneficial (FPC 3.2+ support)
* Maintain compatibility with Java MigLayout behavior

== Rationale for Porting vs TDD

=== Lessons from Row Spanning Implementation

The row spanning feature took significant effort to implement correctly:

* Required studying Java source code (Grid.java) to understand algorithm
* Multiple iterations to get edge cases right
* Complex logic for occupied cell tracking and size distribution
* Risk of diverging from Java behavior

**Insight:** We're already depending on Java source for correctness. Why not make it systematic?

=== Problems with Pure TDD Approach

1. **Slow Progress**: Each feature requires research, implementation, testing, debugging
2. **Reinventing Wheels**: Solving problems already solved in v3, v4...v11
3. **Hidden Complexity**: Many features as complex as row spanning await:
   * Baseline alignment
   * Size groups and component links
   * Dock mode with spans
   * Gap collapse for hidden components
   * Flow mode wrapping
   * Absolute positioning
   * Percentage-based sizing
4. **Edge Cases**: Will miss subtle bugs until production use
5. **Documentation Gap**: v11 docs won't match partial implementation
6. **Version Lag**: Starting from scratch puts us 11 versions behind

=== Advantages of Porting v11

1. **Battle-Tested Logic**: 11 versions of bug fixes and refinements
2. **Complete Feature Set**: All features from day one
3. **HiDPI Support**: Logic units built-in (goal for fpGUI)
4. **Proven Algorithms**: Complex cases already solved correctly
5. **Faster to Production**: Direct translation more mechanical than invention
6. **Perfect Compatibility**: Behaves exactly like Java version
7. **Documentation Match**: Official v11 docs apply directly
8. **Future Updates**: Can track Java releases for improvements
9. **Less Risk**: Algorithmic bugs already found and fixed

=== What We Preserve from Current Implementation

Our existing work remains valuable:

* ✓ `ILayoutManager` interface design
* ✓ `TfpgBaseLayoutManager` helper class
* ✓ `TfpgLayoutConstraint` base class
* ✓ Integration with `TfpgWidget.HandleAlignments`
* ✓ All unit tests (9 passing tests)
* ✓ fpGUI architectural patterns
* ✓ Understanding of MigLayout concepts

**Strategy:** Keep our interface layer, replace implementation internals with v11 algorithms.

=== Design Patterns and Pascal Features

==== Use of Interfaces

fpGUI already uses the interface pattern successfully (`ILayoutManager` + `TfpgBaseLayoutManager`). We should continue this where beneficial:

**Benefits:**

* Reference counting via `TInterfacedObject` - automatic memory management
* Loose coupling - depend on contracts, not implementations
* Testability - easy to mock/stub

**Critical for Fluent API:**

Interfaces are **REQUIRED** for all constraint classes that use fluent API pattern. Without interfaces, the fluent pattern causes memory leaks in Pascal:

[source,pascal]
----
// WITHOUT interfaces - MEMORY LEAK!
lm.RowConstraints := TfpgMigAC.Create.Fill.Grow(100);
// The intermediate TfpgMigAC instance is never freed!

// WITH interfaces - NO LEAK (reference counting)
lm.RowConstraints := TfpgMigAC.Create.Fill.Grow(100);
// Interface reference counting handles cleanup automatically
----

**Where to use interfaces:**

* **REQUIRED**: All fluent API constraint classes (LC, AC, CC)
* Keep `ILayoutManager` for layout managers
* Consider `ILayoutCallback` for LayoutCallback (allows easy stubbing)
* Grid internals can use classes (performance-critical, not exposed to users)

**Interface Design Pattern:**

[source,pascal]
----
type
  // Interface defines the public API
  IfpgMigAC = interface
    ['{GUID-HERE}']
    function Fill: IfpgMigAC;
    function Grow(APriority: Integer): IfpgMigAC;
    function Index(AIndex: Integer): IfpgMigAC;
    function Gap(const AGap: string): IfpgMigAC;
    // Internal access for layout engine
    function GetConstraints: TArray<TfpgMigDimConstraint>;
  end;

  // Implementation with reference counting
  TfpgMigAC = class(TInterfacedObject, IfpgMigAC)
  private
    FConstraints: TObjectList<TfpgMigDimConstraint>;
  public
    constructor Create;
    destructor Destroy; override;
    // Fluent methods return interface, not Self
    function Fill: IfpgMigAC;
    function Grow(APriority: Integer): IfpgMigAC;
    function GetConstraints: TArray<TfpgMigDimConstraint>;
  end;

implementation

function TfpgMigAC.Fill: IfpgMigAC;
begin
  // Modify state
  // Return interface to self for chaining
  Result := Self;
end;
----

This pattern eliminates memory leaks while maintaining the fluent API convenience that Java enjoys with garbage collection.

==== Use of Generics (FPC objfpc mode)

Free Pascal Compiler 3.2+ with `{$mode objfpc}` requires **specialized** type definitions:

**FPC Syntax (objfpc mode):**

[source,pascal]
----
uses
  Generics.Collections;

type
  // Must declare specialized types first
  TfpgMigCompWrapList = specialize TObjectList<TfpgMigCompWrap>;
  TStringIntMap = specialize TDictionary<string, Integer>;
  TIntegerList = specialize TList<Integer>;

  TfpgMigCell = class
  private
    FCompWraps: TfpgMigCompWrapList;  // Use specialized type
  end;
----

**Note:** Unlike Delphi mode, objfpc mode requires explicit `specialize` declarations. Cannot use inline generics like `TObjectList<T>`.

==== Reducing Circular Dependencies

When porting, consider class hierarchy carefully:

**Guideline:** If a field/property could logically belong to `TfpgWidgetBase` instead of `TfpgWidget`, move it there to reduce circular unit dependencies.

**Example from current code:**

* Layout-related fields might be better in `TfpgWidgetBase`
* Reduces coupling between layout manager units and widget units
* Makes testing easier (can test against base class)

**During port, we may refactor:**

* Move layout-related properties higher in hierarchy
* Extract interfaces where it reduces coupling
* Keep backward compatibility via property forwarding if needed

==== Critical Architectural Change: TfpgLayoutConstraint Base Class

**Problem:** The fluent API pattern requires `TInterfacedObject` for automatic reference counting, but the existing `TfpgLayoutConstraint` inherits from `TPersistent`, which does **not** provide reference counting.

**Testing confirms:** `TPersistent` does not implement `IInterface` methods (`QueryInterface`, `_AddRef`, `_Release`), so classes inheriting from `TPersistent` cannot use interface reference counting.

**Solution:** Change `TfpgLayoutConstraint` base class in `fpg_layouttypes.pas`:

[source,pascal]
----
// Before:
TfpgLayoutConstraint = class(TPersistent)
end;

// After:
TfpgLayoutConstraint = class(TInterfacedObject)
end;
----

**Rationale:**

* Enables reference counting for all layout constraint classes
* `TPersistent` was likely chosen for `Assign()` method and RTTI (`{$M+}`)
* Layout constraints don't need `TPersistent`'s streaming/component features
* `TInterfacedObject` provides the reference counting required for fluent API
* Should be backward compatible (existing constraint classes gain reference counting)

**Impact:**

* All existing layout constraints (e.g., flow layout, future layouts) can use interface pattern
* MigLayout constraints can cleanly inherit: `TfpgMigCC = class(TfpgLayoutConstraint, IfpgMigCC)`
* No multiple inheritance issues
* Enables future fluent APIs in other layout managers

=== Key Differences: Java vs Pascal

==== Collection Types

[source,java]
----
// Java
ArrayList<CompWrap> compWraps = new ArrayList<>();
HashMap<String, Integer> map = new HashMap<>();
TreeSet<Integer> indexes = new TreeSet<>();
----

[source,pascal]
----
// Pascal (using Generics.Collections)
compWraps: TList<TCompWrap>;
map: TDictionary<string, Integer>;
indexes: TList<Integer>; // sorted manually or use custom comparator
----

==== Nullable Types

[source,java]
----
// Java
Float growPriority = null;
if (growPriority != null) { ... }
----

[source,pascal]
----
// Pascal (use pointer or variant or custom nullable record)
type
  TNullableFloat = record
    HasValue: Boolean;
    Value: Single;
  end;

var
  growPriority: TNullableFloat;
if growPriority.HasValue then ...
----

==== Interface vs Abstract Class

Java uses interfaces with default methods (since Java 8). Pascal doesn't have default interface methods, so we'll use abstract classes where appropriate or split into interface + helper class pattern (already established with `ILayoutManager` + `TfpgBaseLayoutManager`).

==== String Handling

Java strings are immutable objects. Pascal strings are mutable. Need to be careful with string parsing and ensure proper copying where needed.

==== Platform Detection

[source,java]
----
// Java
String osName = System.getProperty("os.name");
----

[source,pascal]
----
// Pascal
{$IFDEF WINDOWS}
  // Windows-specific
{$ENDIF}
{$IFDEF UNIX}
  // Unix-specific
{$ENDIF}
----

== Java to Pascal Porting Guidelines

=== Naming Conventions

[source,java]
----
// Java
public class ComponentWrapper {
    private int minWidth;
    public int getMinWidth() { return minWidth; }
    public void setMinWidth(int value) { minWidth = value; }
}
----

[source,pascal]
----
// Pascal
type
  TfpgMigComponentWrapper = class
  private
    FMinWidth: Integer;
  public
    property MinWidth: Integer read FMinWidth write FMinWidth;
  end;
----

**Rules:**

* Class names: `ClassName` → `TfpgMigClassName`
* Private fields: `fieldName` → `FFieldName`
* Methods: `methodName()` → `MethodName()`
* Properties: `getProperty()/setProperty()` → `property Property`
* Constants: `CONSTANT_NAME` → `CONSTANT_NAME` (keep same)

=== Collection Translation

[source,java]
----
// Java
ArrayList<Cell> cells = new ArrayList<>();
HashMap<String, Integer> map = new HashMap<>();
----

[source,pascal]
----
// Pascal
uses Generics.Collections;

var
  cells: TObjectList<TfpgMigCell>;  // owns objects
  map: TDictionary<string, Integer>;

begin
  cells := TObjectList<TfpgMigCell>.Create(True); // True = owns objects
  map := TDictionary<string, Integer>.Create;
  try
    // use collections
  finally
    cells.Free;
    map.Free;
  end;
end;
----

**Memory Management:**

* Java: garbage collected
* Pascal: manual - always Free in finally blocks
* Use TObjectList with OwnsObjects=True where appropriate

=== Null Handling

[source,java]
----
// Java
Float value = null;
if (value != null) {
    useValue(value);
}
----

[source,pascal]
----
// Pascal - Option 1: Pointer
var
  value: PSingle;
begin
  value := nil;
  if value <> nil then
    UseValue(value^);
end;

// Pascal - Option 2: Nullable record (recommended)
type
  TNullableSingle = record
    HasValue: Boolean;
    Value: Single;
    class function Null: TNullableSingle; static;
    class function Of(AValue: Single): TNullableSingle; static;
  end;

var
  value: TNullableSingle;
begin
  value := TNullableSingle.Null;
  if value.HasValue then
    UseValue(value.Value);
end;

=== Interface vs Class

Java code uses interfaces extensively. Pascal strategy:

1. Keep `ILayoutManager` interface pattern for public API
2. Use abstract classes for internal hierarchy (Grid, etc.)
3. Use helper classes where Java uses default interface methods
