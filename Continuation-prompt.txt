Important Reminders

1. Follow Java code line-by-line - The Java MigLayout v11 source is our source of truth
2. Empty arrays are not null in Pascal - Check Length(array) > 0 instead of array <> nil
3. Test-Driven Development - We've found many bugs by creating tests first
4. Memory management - Use "Clone-on-Set" strategy for BoundSize/UnitValue to avoid leaks
5. When using generics, you need to define specialized types before you can use them in
   method declarations.
6. Unit tests are run via: pasbuild test -p unix,agg,debug
7. We are mainly testing with the X11+AggCanvas backend, but occasionally test with X11
   (AggCanvas disabled)
8. Java mig code (as reference) can be found in: prototypes/miglayout/mig-java-latest/core
   & prototypes/miglayout/mig-java-latest/swing
9. Java uses TreeSet<Integer> for row/col indexes (auto-sort + auto-deduplicate).
   Pascal uses TList<Integer> - requires manual sort + dedup in BuildIndexes.
10. EncodeCellKey/DecodeCellKey does NOT handle negative coordinates (FPC shr is logical).
    Docking cells use negative coords; BuildIndexes skips them (their indexes come from
    AddDockingCell). If you ever need to decode negative coords, this encoding must be fixed.
11. Do NOT add WriteLn debug output to production mig code. If needed temporarily, remove
    before committing.

Important Memory Ownership Rules:
  - ParseUnitValueOrAlign returns singleton UnitValue constants — do NOT free them.
  - ParseUnitValue creates NEW instances — callers own and must free them.
  - BoundSize.Create always clones UnitValues — safe to free originals after.
  - DimConstraint.FAlign and LC.FAlignX/FAlignY store singleton refs — NOT freed in destructors.

Docking coordinate system:
  - Normal grid:    coordinates 0 to MAX_GRID (30000)
  - Dock North/West: negative coords from -MAX_DOCK_GRID (-32767)
  - Dock South/East: positive coords up to MAX_DOCK_GRID (32767)
  - DockOff = count of row/col indexes outside normal grid range
  - DOCK_DIM_CONSTRAINT singleton used for dock rows/columns
