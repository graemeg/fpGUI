Critical Bugs Identified (2025-11-18)

Priority 1 - BLOCKING PRODUCTION USE:
1. ❌ Cell spanning doesn't calculate component sizes (DISCOVERED 2025-11-18)
   - Grid placement respects spans (components positioned correctly)
   - But LayoutInOneDim doesn't allocate combined width/height for spanning components
   - Example: Component with SpanX(2) should get width = col1 + gap + col2, but gets col1 only
   - Workaround: Manually set component Width/Height large enough (as in frm_spanning.pas demo)
   - Root cause: LayoutInOneDim and layout methods don't check component span when sizing
   - Fix needed: Port Java Grid.java spanning logic from layoutParallel/layoutSerial methods
   - Impact: Dynamic layouts relying on MigLayout to size spanning components fail
   - Test failure: TTestMigQuickStart.TestCellSpanning (comp2.Width > comp1.Width fails)
   - Location: fpg_miglayout.pas LayoutInOneDim, LayoutParallel, LayoutSerial methods

2. ❌ UnitValue.GetPixels() does NOT handle operations (ADD, SUB, MUL, DIV, MIN, MAX, MID)
   - Currently only handles STATIC operations, returns 0 for everything else
   - This breaks string constraints like: .Width('max(150px,30%)')
   - Root cause: Missing implementation of lines 382-401 from UnitValue.java
   - Fix needed: Recursively evaluate subUnits[0] and subUnits[1], apply operation
   - Impact: All operation-based constraints fail silently
   - Location: fpg_mig_unitvalue.pas:306-372 (GetPixels method)

Priority 2 - MEMORY LEAKS:
3. ⚠️ Memory leaks detected: 992 unfreed memory blocks (292,299 bytes) - IMPROVED
   - Was 1129 blocks, then 802, now 992 (still investigating pattern)
   - Fixed 72 leaks in ParseBoundSize by adding try-finally blocks (2025-11-18)
   - Fixed BoundSize to always clone/free UnitValues (simpler ownership model)
   - Remaining leaks likely from ParseInsets returning singleton references
   - Most remaining are fpGUI core initialization (fonts, styles) ~700 blocks
   - Access violation on test exit (heaptrc reporting issue)
   - Location: Remaining leaks throughout constraint parser and LC/CC classes

Priority 3 - INCOMPLETE FEATURES:

   - Visual padding, flow specs, callbacks
   - Not blocking basic layout functionality but needed for 100% compatibility

Analysis Details:
- Compared Pascal GetPixels() with Java getPixelsExact() (UnitValue.java:293-404)
- Java handles operations in lines 382-401 by recursively calling getPixelsExact on subUnits
- Pascal implementation stops at line 371 with "Result := 0; // Other units not implemented yet"
- This explains why frm_parser.pas operations don't work (max, min, arithmetic ops)
